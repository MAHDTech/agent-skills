# Custom skill invocation audit

Date: 2026-10-25.

<!-- cspell:ignore autoinvoke -->

## Scope and result

Reviewed the complete bodies, discovery descriptions, and Codex sidecars of all 76 promoted custom skills. Two parallel reviewers covered engineering, game development, tooling, and workflow categories; a third researched host behavior and added a regression check. The primary reviewer covered authoring skills and reconciled parent/helper relationships.

The result is 57 skills available for automatic selection and 19 explicit-only skills. Automatic selection means the model may choose a relevant skill and then load its instructions; it does not mean loading every skill body at startup. Invocation policy does not authorize actions beyond the user's request.

Vendor skills are entirely excluded: descriptions and policies belong to the vendor, with no local overrides. Archived skills and drafts are inactive and unchanged. This is a description and invocation audit, rather than a full retirement, cross-reference, or body-rewrite pass.

All promoted custom skills now have an explicit boolean `policy.allow_implicit_invocation` in `agents/openai.yaml`, matching the inverse of `disable-model-invocation` in `SKILL.md`. Missing Claude flags mean automatic selection is allowed. Explicit-only bodies also state their user-request boundary for hosts without a verified policy control.

## Discovery and host compatibility

The shared discovery field is `description` in `SKILL.md`. Codex `interface.short_description` is a separate UI label; shortening that label alone would leave discovery text unchanged. Selection is based on the model interpreting the description and request, rather than a repository-defined keyword matcher. Full instructions are loaded progressively when selected. See the cited [compatibility reference](../../skills/authoring/skill-creator/resources/manual/invocation-compatibility.md) for host-specific details and sources.

| Host                                  | Explicit-only control                                                             | Limitation                                                                                                                             |
| ------------------------------------- | --------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Codex                                 | `policy.allow_implicit_invocation: false` in `agents/openai.yaml`                 | Use an explicit skill invocation such as `$name`; the UI description is separate.                                                      |
| Claude Code                           | `disable-model-invocation: true` in `SKILL.md`                                    | The description is excluded from automatic discovery; `/name` remains available.                                                       |
| OpenCode V2 development documentation | `metadata.opencode/autoinvoke: false`, with the Claude flag supported as an alias | The OpenCode-specific value takes precedence; this repo uses the Claude alias.                                                         |
| OpenCode V1 documentation             | No per-skill equivalent verified                                                  | Skill permissions can deny loading entirely, including manual use.                                                                     |
| Antigravity                           | No implicit opt-out documented in the reviewed sources                            | `disable-slash-command: true` hides manual commands while retaining model discovery, so it does not implement explicit-only selection. |
| Goose native skills                   | No equivalent verified in docs or parser/client source                            | Policies in other hosts' metadata are not a verified selection control.                                                                |

The manual boundary in skill bodies is advisory on unsupported hosts. This audit does not claim a universal enforcement mechanism, zero context cost, or exact billing savings.

## Selection decisions

Manual workflows publish externally, change skill lifecycle or installed state, establish persistent behavior, or orchestrate a broad multi-phase effort. The catalog audit and router are explicit whole-collection workflows. Automatic skills supply focused expertise, bounded analysis, or local task helpers.

Required helpers stay reachable from an explicitly started parent workflow. In particular, `grilling` can serve the approved planning interview in `software-factory` or `wayfinder`, and `git-resolve-conflicts` can repair existing conflicts during `git-update-branch`. Their descriptions constrain that selection; starting a new interview, merge, or publication is not implied by incidental keywords.

Explicit-only skills should be selected by name on hosts that enforce this boundary. The human-facing discovery summary still explains their purpose. A parent workflow can offer the next manual step to the user; it must not bypass the host's invocation restriction by reading a disabled skill directly.

### Policy corrections

The new regression test first failed on 11 existing problems: nine disagreements between Claude and Codex, plus missing explicit Codex booleans for `jj` and `oak`.

- Aligned missing Claude manual flags for `skill-archive`, `gh-release-notes`, `gh-submit-review`, `git-update-branch`, `total-recall`, `tars-goal`, and `install-skills`.
- Made `wtf` and `scratchpad` automatic in both hosts: they are bounded response and temporary-artifact helpers.
- Added explicit automatic Codex policies for `jj` and `oak` and shortened their oversized UI labels.
- Changed `git-resolve-conflicts`, `handoff`, and `store-plan` to automatic for focused local work and required handoffs.
- Changed `skill-audit` to explicit-only because editing one skill should not start a collection-wide sweep.
- Kept `grilling` automatic with a narrow explicit-request or approved-parent trigger, preserving its planning dependencies.

### Description changes

Discovery descriptions decreased from 23,363 to 13,596 characters, a 41.8% reduction. Revised descriptions are 100-220 characters. This is a measured character count, not a token or cost estimate. Some previously terse summaries gained useful selection boundaries. Long version lists and command inventories remain in the skill bodies.

## Authoring and regression prevention

The skill creator now requires concise discovery text, distinguishes discovery from UI descriptions, requires both host policies to agree, and explains unsupported-host limits. The audit meta skill and repository instructions preserve those rules for future work. A Rust integration test reads the promoted custom catalog, validates each sidecar, requires an explicit boolean, and compares it with the parsed Claude flag. Vendors and drafts are excluded before reading; archives are outside the active tree.

Run the focused policy check from the development environment:

```bash
scripts/run-tests.sh -E 'test(promoted_custom_skills_have_matching_explicit_invocation_policies)'
```

The test verifies configuration consistency, not whether every model will select the desired skill for every possible prompt. Manual host smoke checks should confirm that explicit-only skills remain callable by name and that relevant specialist descriptions are discoverable.

## Incidental findings left for a separate body audit

- `total-recall` calls its decision trail append-only but also describes pruning rows during its audit. Resolve that retention contradiction before relying on the trail as immutable evidence.
- `tars-run-factory` references `/tars-regress-run`, which is absent from this custom catalog. Confirm whether it is an external command or replace the handoff.
- `sculpt-code` emphasizes deleting redundant comments, while `code-comments` permits explanations of non-obvious intent. Keep the scoped description boundary and reconcile their detailed advice if both are selected.
- `research` requires background delegation, and `tdd` requires an interface/seam confirmation. These may add workflow gates to otherwise authorized work; review those bodies separately rather than changing them as part of metadata cleanup.

No skills were archived, merged, renamed, or given vendor overrides in this audit.
