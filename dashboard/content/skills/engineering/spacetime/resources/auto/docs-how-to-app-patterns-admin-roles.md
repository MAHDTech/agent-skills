<p>In this guide, you&#x27;ll add moderators and admins to a chat: moderators can delete any message, and admins can also clear the whole chat. You&#x27;ll store each user&#x27;s role in a private table, check it at the start of each reducer that needs it, and use a <a class="" href="/docs/functions/views">view</a> to tell each client its own role.</p>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="how-it-works">How it works<a href="#how-it-works" class="hash-link" aria-label="Direct link to How it works" title="Direct link to How it works" translate="no">​</a></h2>
\<ul\>
<li class="">A private <code>user_role</code> table holds the role of each user who has one: <code>Moderator</code> or <code>Admin</code>. Users without a row are regular users.</li>
<li class="">Each reducer that needs a role checks the caller&#x27;s role first, and returns an error if it&#x27;s missing. Admins can do everything moderators can.</li>
<li class="">The <code>set_role</code> and <code>remove_role</code> reducers give and take away roles.</li>
<li class="">A <code>my_role</code> view returns the caller&#x27;s role, so the client can show moderation buttons only to the users who can use them.</li>
</ul>
<p>The checks in the reducers are what keep regular users out. Hiding a button on the client only changes what the user sees: anyone can call your reducers directly, from a modified client or the CLI.</p>

<p>Add two helpers that reducers call before doing anything else:</p>
\<ul\>
<li class=""><code>require_moderator</code> returns an error unless the caller is a moderator or an admin.</li>
<li class=""><code>require_admin</code> returns an error unless the caller is an admin.</li>

<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="define-the-views">Define the views<a href="#define-the-views" class="hash-link" aria-label="Direct link to Define the views" title="Direct link to Define the views" translate="no">​</a></h2>
<p>Add two public views:</p>
\<ul\>
<li class=""><code>my_role</code> returns the caller&#x27;s row in <code>user_role</code>, so each client knows its own role. It depends on who&#x27;s asking, so it isn&#x27;t anonymous: each user gets their own result.</li>
<li class=""><code>messages</code> returns every message. It&#x27;s anonymous, so SpacetimeDB computes it once and shares it with every client.</li>
</ul>
<p>Both return a query, which SpacetimeDB keeps up to date the same way as a subscription query: when a user&#x27;s role changes, their <code>my_role</code> changes right away.</p>

<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="give-yourself-a-role">Give yourself a role<a href="#give-yourself-a-role" class="hash-link" aria-label="Direct link to Give yourself a role" title="Direct link to Give yourself a role" translate="no">​</a></h2>
<p>To try the moderation tools, give your app&#x27;s identity a role from the CLI:</p>
\<ol\>
<li class="">Run your app, and copy the identity it prints when it connects.</li>
<li class="">Call <code>set_role</code> with that identity, prefixed with <code>0x</code>. Role values are written in lowercase, <code>moderator</code> or <code>admin</code>:</li>
</ol>
<pre tabindex="0" class="codeBlockStandalone_LlrK thin-scrollbar codeBlockContainer_hFbQ theme-code-block" style="--prism-color:#bfc7d5;--prism-background-color:#292d3e"><code class="codeBlockLines_JqGU"><span class="line"><span style="color:#50FA7B">spacetime</span><span style="color:#F1FA8C"> call</span><span style="color:#F1FA8C"> my-app</span><span style="color:#F1FA8C"> set_role</span><span style="color:#F1FA8C"> 0x</span><span style="color:#FF79C6"><</span><span style="color:#F1FA8C">your</span><span style="color:#F1FA8C"> app</span><span style="color:#F1FA8C"> identit</span><span style="color:#F8F8F2">y</span><span style="color:#FF79C6">></span><span style="color:#E9F284"> &#x27;</span><span style="color:#F1FA8C">{"admin": []}</span><span style="color:#E9F284">&#x27;</span></span></code></pre>
<p>Your app&#x27;s <code>my_role</code> changes as soon as the call succeeds, and the moderation tools appear.</p>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="whats-next">What&#x27;s next?<a href="#whats-next" class="hash-link" aria-label="Direct link to What&#x27;s next?" title="Direct link to What&#x27;s next?" translate="no">​</a></h2>
<p>You now have moderators and admins in your app:</p>
\<ul\>
<li class="">Roles live in a private table, and each reducer that needs one checks it before doing anything else.</li>
<li class="">A <code>my_role</code> view tells each client its own role, so the client only shows the tools the user can use.</li>
</ul>
<p>To adapt it to your app:</p>
\<ul\>
<li class=""><strong>Protect <code>set_role</code> and <code>remove_role</code>.</strong> Decide who can give roles, for example only admins, and check it at the start of both reducers, the same way <code>clear_messages</code> does.</li>
<li class=""><strong>Ban users.</strong> Add a private <code>banned_user</code> table that moderators fill, and check it at the start of <code>send_message</code>.</li>
<li class=""><strong>Keep a log of moderation actions.</strong> Insert a row into a private <code>moderation_log</code> table in each moderation reducer, with who did what and when.</li>
<li class=""><strong>Show who the moderators are.</strong> Add an anonymous view that returns every row of <code>user_role</code>, so clients can show a badge next to moderators&#x27; messages.</li>
</ul>
