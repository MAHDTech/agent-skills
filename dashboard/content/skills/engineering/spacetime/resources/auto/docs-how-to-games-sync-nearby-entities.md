<p>In this guide, you&#x27;ll make each client receive only the players near it, rather than every player in the world. You&#x27;ll split the world into square chunks, store the chunk each player is in, and have each client <a class="" href="/docs/clients/subscriptions">subscribe</a> to the chunks around its player, moving that subscription as the player moves.</p>

<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="how-it-works">How it works<a href="#how-it-works" class="hash-link" aria-label="Direct link to How it works" title="Direct link to How it works" translate="no">​</a></h2>
\<ul\>
<li class="">The world is a grid of square chunks, each 100 units wide.</li>
<li class="">A public <code>player</code> table holds each player&#x27;s position and the chunk they&#x27;re in, with an index on the chunk.</li>
<li class="">A <code>move_player</code> reducer updates the player&#x27;s position and chunk.</li>
<li class="">Each client subscribes to its own row, and to the players in its chunk and the 8 chunks around it.</li>
<li class="">When the player enters a new chunk, the client subscribes to the new chunks, then drops its old subscription.</li>
</ul>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="define-the-table">Define the table<a href="#define-the-table" class="hash-link" aria-label="Direct link to Define the table" title="Direct link to Define the table" translate="no">​</a></h2>
<p>Add a <code>player</code> table with one row per online player. <code>chunk</code> is a single number that identifies a chunk: <code>chunk_y * 100 + chunk_x</code>. Its index lets SpacetimeDB find the players in a chunk directly, without scanning the whole table.</p>
<p>The world here is 10,000 units wide, or 100 chunks per side. Use the size of your own world.</p>

<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="track-each-players-chunk">Track each player&#x27;s chunk<a href="#track-each-players-chunk" class="hash-link" aria-label="Direct link to Track each player&#x27;s chunk" title="Direct link to Track each player&#x27;s chunk" translate="no">​</a></h2>
<p>Add a <code>chunk_at</code> function that returns the chunk containing a position, and keep <code>chunk</code> up to date wherever a player&#x27;s position changes:</p>
\<ul\>
<li class="">The <code>client_connected</code> <a class="" href="/docs/functions/reducers/lifecycle">lifecycle reducer</a> adds the player in the middle of the world. If the player already has a row, for example because they&#x27;re connected from two tabs, it keeps it.</li>
<li class="">The <code>client_disconnected</code> reducer removes the player, so clients only see players who are online.</li>
<li class="">The <code>move_player</code> reducer rejects positions outside the world, then stores the new position and its chunk.</li>
</ul>
<p><code>move_player</code> accepts any position in the world. In your game, also check that the player didn&#x27;t move further than they can.</p>

<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="subscribe-to-nearby-players">Subscribe to nearby players<a href="#subscribe-to-nearby-players" class="hash-link" aria-label="Direct link to Subscribe to nearby players" title="Direct link to Subscribe to nearby players" translate="no">​</a></h2>
<p>The client keeps two subscriptions:</p>
\<ul\>
<li class=""><strong>Its own row</strong>, for its whole session. That&#x27;s how it learns which chunk the player is in.</li>
<li class=""><strong>The nearby chunks</strong>: one query per chunk, for the player&#x27;s chunk and the chunks around it. Each query keeps only the rows whose <code>chunk</code> equals one value, which is the cheapest kind of query to keep up to date. When a player moves, SpacetimeDB only checks the subscriptions to that player&#x27;s old and new chunks, however many clients are subscribed to other chunks.</li>
</ul>
<p>When the player&#x27;s own row shows they entered a new chunk, the client subscribes to the chunks around it. It drops the old subscription only once the new one is applied. Players in both areas then stay in the client cache, rather than being removed and added back.</p>
<p>The client cache now holds only the nearby players. Draw them from it each frame. When a player leaves the area, the client receives a delete for their row, so remove them from the screen in your delete callback.</p>

<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="whats-next">What&#x27;s next?<a href="#whats-next" class="hash-link" aria-label="Direct link to What&#x27;s next?" title="Direct link to What&#x27;s next?" translate="no">​</a></h2>
<p>Each client now receives only the players around it:</p>
\<ul\>
<li class="">Every player row stores its chunk, in an indexed column that <code>move_player</code> keeps up to date.</li>
<li class="">Clients subscribe to the 9 chunks around their player, with one query per chunk.</li>
<li class="">When the player changes chunk, the client subscribes to the new chunks before dropping the old ones.</li>
</ul>
<p>To adapt it to your game:</p>
\<ul\>
<li class=""><strong>Pick the chunk size from your view distance.</strong> The 3×3 area only covers the view distance in every direction if chunks are at least as wide as it. Smaller chunks send fewer players, but clients change subscriptions more often.</li>
<li class=""><strong>Sync other things the same way.</strong> Give NPCs, items or projectiles a <code>chunk</code> column with an index, and add a query per chunk for their tables to the same subscription.</li>
<li class=""><strong>Update chunks in your game tick.</strong> If a <a class="" href="/docs/how-to/games/fixed-rate-game-tick">fixed-rate game tick</a> moves your entities, recompute their chunk there too.</li>
</ul>
<p>To learn more about the features used here, see <a class="" href="/docs/clients/subscriptions">Subscriptions</a>, <a class="" href="/docs/tables/indexes">Indexes</a> and <a class="" href="/docs/functions/reducers/lifecycle">Lifecycle Reducers</a>.</p>
