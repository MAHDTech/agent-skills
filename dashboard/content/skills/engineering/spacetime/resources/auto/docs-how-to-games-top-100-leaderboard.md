<p>In this guide, you&#x27;ll build a leaderboard that shows the 100 best scores in your game and updates live on every client. You&#x27;ll use an <a class="" href="/docs/tables/indexes">index</a> to read scores, an anonymous <a class="" href="/docs/functions/views">view</a> to pick the top 100, and a <a class="" href="/docs/clients/subscriptions">subscription</a> to keep each client up to date.</p>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="how-it-works">How it works<a href="#how-it-works" class="hash-link" aria-label="Direct link to How it works" title="Direct link to How it works" translate="no">​</a></h2>
\<ul\>
<li class="">A private <code>player_score</code> table stores each player&#x27;s best score, with an index on the score.</li>
<li class="">A <code>submit_score</code> reducer records a new score.</li>
<li class="">A public <code>top_100</code> view reads every score through the index and returns the 100 highest.</li>
<li class="">Clients subscribe to <code>top_100</code>, never to <code>player_score</code> itself.</li>
</ul>
<p>The view is anonymous: it returns the same rows no matter who asks. SpacetimeDB computes it once and shares the result with every subscribed client, instead of computing it once per client.</p>

<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="what-this-view-costs">What this view costs<a href="#what-this-view-costs" class="hash-link" aria-label="Direct link to What this view costs" title="Direct link to What this view costs" translate="no">​</a></h3>
<p>The range query covers every score, so the view reads the whole <code>player_score</code> table each time it runs. SpacetimeDB re-runs it whenever a row in <code>player_score</code> changes. Because the view is anonymous, that happens once per change, not once per subscribed client.</p>
<p>Because the view reads and sorts the whole table every time a score changes, its cost grows with your player count. That&#x27;s fine for small and medium games. If you expect a very large player base, measure how long score submissions take as the table grows. See <a class="" href="/docs/functions/views#performance-considerations">Performance Considerations</a> for more on what makes a view expensive.</p>

<p><code>onInsert</code> and <code>onDelete</code> run once for each row that changes. When a new score enters the top 100, the client receives one insert for the new row and one delete for the score that dropped out, so the leaderboard is re-rendered twice. If rendering is expensive, re-render at most once per frame instead.</p>
<p>In TypeScript, the rows of <code>top_100</code> keep the primary key of <code>player_score</code>. So when a player already in the top 100 improves their score, the client receives an update for their row instead of a delete and an insert, and <code>onUpdate</code> re-renders the leaderboard.</p>

<p>You now have a leaderboard that stays live on every client:</p>
\<ul\>
<li class="">An index on <code>score</code> lets the view read the scores.</li>
<li class="">An anonymous view sorts them and keeps the top 100, computed once for all clients.</li>
<li class="">Clients subscribe to the view and sort the rows again before displaying them.</li>
</ul>
