<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="inserting-schedules">Inserting Schedules<a href="#inserting-schedules" class="hash-link" aria-label="Direct link to Inserting Schedules" title="Direct link to Inserting Schedules" translate="no">​</a></h2>
<p>To schedule an action, insert a row into the schedule table with a <code>scheduled_at</code> value. You can schedule actions to run:</p>
\<ul\>
<li class=""><strong>At intervals</strong> - Execute repeatedly at fixed time intervals (e.g., every 5 seconds)</li>
<li class=""><strong>At specific times</strong> - Execute once at an absolute timestamp</li>
</ul>
<p>Interval schedules are anchored to their intended execution times. In the current implementation, if the database is busy or offline long enough to miss one or more interval ticks, SpacetimeDB schedules the next future tick rather than running missed ticks back-to-back or drifting the schedule from the delayed execution time.</p>

<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="how-it-works">How It Works<a href="#how-it-works" class="hash-link" aria-label="Direct link to How It Works" title="Direct link to How It Works" translate="no">​</a></h2>
\<ol\>
<li class=""><strong>Insert a row</strong> with a <code>ScheduleAt</code> value</li>
<li class=""><strong>SpacetimeDB monitors</strong> the schedule table</li>
<li class=""><strong>When the time arrives</strong>, the specified reducer/procedure is automatically called with the row as a parameter</li>
<li class=""><strong>The row is typically deleted</strong> or updated by the reducer after processing</li>
</ol>
<p>For interval schedules, the current implementation calculates the next run from the previous intended run time. Missed interval ticks are skipped, so a delayed scheduled reducer or procedure resumes on the next future interval boundary.</p>
<p>When multiple schedule rows have already expired by the time SpacetimeDB observes them, their dispatch order is not guaranteed to match <code>scheduled_at</code> order. If application behavior depends on ordering, store an explicit sequence or timestamp in the scheduled row and handle ordering in your module logic.</p>
<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="row-lifecycle">Row Lifecycle<a href="#row-lifecycle" class="hash-link" aria-label="Direct link to Row Lifecycle" title="Direct link to Row Lifecycle" translate="no">​</a></h3>
<p>SpacetimeDB passes the schedule row to the scheduled reducer or procedure as an argument. One-shot schedule rows are removed at different times depending on the kind of function being called:</p>
\<ul\>
<li class="">Scheduled procedures delete the row before execution, so <code>schedule_table.find(scheduled_id)</code> returns <code>null</code> and <code>.update()</code> fails.</li>
<li class="">Scheduled reducers delete the row after execution, so the row is visible in the schedule table while the reducer runs.</li>
<li class="">Interval schedules are never deleted automatically. Only one-shot schedules are removed after they run.</li>
</ul>

<li class=""><strong>Expiring content</strong> - Automatically remove or archive old data</li>
