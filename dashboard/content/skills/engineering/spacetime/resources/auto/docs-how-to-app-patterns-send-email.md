class="admonitionContent_STxx"><p>You need a module and a client connected to it, and an API key from an email provider. This guide uses <a href="https://resend.com" target="_blank" rel="noopener noreferrer" class="">Resend</a>. <p>In this guide, you&#x27;ll send emails to players from your module, such as a welcome email when a player adds their address. Your module calls your email provider&#x27;s HTTP API, so the provider&#x27;s API key never reaches the client. You&#x27;ll queue each email in a <a class="" href="/docs/tables/schedule-tables">schedule table</a>, send it from a <a class="" href="/docs/functions/procedures">procedure</a>, and store the API key in an <a class="" href="/docs/databases/environment-variables">environment variable</a>.</p>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="how-it-works">How it works<a href="#how-it-works" class="hash-link" aria-label="Direct link to How it works" title="Direct link to How it works" translate="no">​</a></h2>
\<ul\>
<li class="">An <code>EMAIL_API_KEY</code> environment variable stores your provider API key on the database. You set it when you publish.</li>
<li class="">A private <code>player_email</code> table holds each player&#x27;s email address. A <code>set_email</code> reducer saves it.</li>
<li class="">A private <code>email_outbox</code> schedule table holds the emails to send. A <code>queue_email</code> function adds one, from any reducer.</li>
<li class="">Each row of <code>email_outbox</code> runs the <code>send_email</code> procedure, which sends the email to your provider. If the provider can&#x27;t take it right now, <code>send_email</code> queues it again a minute later, up to 3 attempts in all.</li>
</ul>
<p>Reducers can&#x27;t make HTTP requests, because they run inside a transaction, so they queue emails instead of sending them. The procedure only sends an email once the transaction that queued it has committed. If a reducer fails, its changes are undone, including its rows in <code>email_outbox</code>, so its emails are never sent.</p>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="define-the-tables-and-the-api-key">Define the tables and the API key<a href="#define-the-tables-and-the-api-key" class="hash-link" aria-label="Direct link to Define the tables and the API key" title="Direct link to Define the tables and the API key" translate="no">​</a></h2>
<p>Declare an <code>EMAIL_API_KEY</code> environment variable in your module. It&#x27;s required, so SpacetimeDB refuses to publish the module without a value, and your procedure can always read it.</p>
<p>Then add the two tables. Both are private, so clients can&#x27;t read anyone&#x27;s address, or the emails waiting to be sent:</p>
\<ul\>
<li class=""><code>player_email</code> has one row per player who added an address.</li>
<li class=""><code>email_outbox</code> is the schedule table. Each row is an email: its recipient, subject and text, and <code>attempt</code>, which counts the times it has been tried. Its <code>scheduled_at</code> column says when to send it, and SpacetimeDB then calls <code>send_email</code> with the row.</li>
</ul>

<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="send-queued-emails">Send queued emails<a href="#send-queued-emails" class="hash-link" aria-label="Direct link to Send queued emails" title="Direct link to Send queued emails" translate="no">​</a></h2>
<p>Add a <code>post_email</code> function that sends an email to Resend&#x27;s <a href="https://resend.com/docs/api-reference/emails/send-email" target="_blank" rel="noopener noreferrer" class="">send email API</a>, and returns the HTTP status of the reply, or 0 if the request didn&#x27;t get a reply. It&#x27;s the only provider-specific code: other providers, such as Postmark, SendGrid or Amazon SES, work the same way, with a different URL, headers and body.</p>
<p>Replace the <code>from</code> address with one on a domain you&#x27;ve verified with your provider. Providers reject emails from other domains.</p>
<p>Then add the <code>send_email</code> procedure. SpacetimeDB calls it with each row of <code>email_outbox</code> when the row&#x27;s time comes, and deletes the row first. <code>send_email</code> sends the email with <code>post_email</code>, then looks at the status:</p>
\<ul\>
<li class="">A 2xx status means the provider accepted the email.</li>
<li class="">No reply, a 429 status (too many requests) or a 5xx status (a server error) means the provider couldn&#x27;t take the email right now. <code>send_email</code> inserts it again, a minute later, until it has tried 3 times.</li>
<li class="">Any other status means the provider rejected the email, for example because the address is invalid, or the API key is wrong. Trying again wouldn&#x27;t help, so <code>send_email</code> logs the status and drops the email.</li>
</ul>

<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="whats-next">What&#x27;s next?<a href="#whats-next" class="hash-link" aria-label="Direct link to What&#x27;s next?" title="Direct link to What&#x27;s next?" translate="no">​</a></h2>
<p>You now send emails from your module:</p>
\<ul\>
<li class="">Reducers queue emails in a private schedule table, so an email only goes out if the change that asked for it commits.</li>
<li class="">A scheduled procedure sends each email, with the API key from an environment variable, and tries again when the provider can&#x27;t take it right now.</li>
<li class="">Players&#x27; addresses are in a private table, and clients can&#x27;t send emails directly.</li>
</ul>
<p>To adapt it to your app:</p>
\<ul\>
<li class=""><strong>Notify players who aren&#x27;t online.</strong> Call <code>queue_email</code> from the reducers where something happens that a player shouldn&#x27;t miss, such as <code>send_direct_message</code> in <a class="" href="/docs/how-to/social/chat-rooms-and-dms">Chat rooms and private DMs</a>. To only email players who aren&#x27;t connected, record who is online with the <code>client_connected</code> and <code>client_disconnected</code> <a class="" href="/docs/functions/reducers/lifecycle">lifecycle reducers</a>.</li>
<li class=""><strong>Confirm addresses.</strong> Add a code to <code>player_email</code>, send it in the welcome email, and add a reducer that marks the address as confirmed when the player enters it. Only send other emails to confirmed addresses.</li>
<li class=""><strong>Duplicate emails.</strong> If the provider accepts an email but its reply is lost, <code>send_email</code> sends it again. To avoid that, store an id with each email that stays the same across attempts, and send it in Resend&#x27;s <code>Idempotency-Key</code> header.</li>
<li class=""><strong>HTML emails.</strong> Send an <code>html</code> field along with <code>text</code>. Keep <code>text</code> for email apps that don&#x27;t show HTML.</li>
<li class=""><strong>Unsubscribe.</strong> Add a reducer that deletes the caller&#x27;s <code>player_email</code> row, and tell players about it in each email.</li>
<li class=""><strong>Track delivery.</strong> In a TypeScript module, the <a href="https://spacetimedb.com/submodules/resend" target="_blank" rel="noopener noreferrer" class="">Resend submodule</a>, a package you add to your module, sends email through Resend and stores whether each email was delivered, delayed or bounced, from Resend&#x27;s webhooks.</li>
<li class=""><strong>Wait longer between attempts.</strong> In a TypeScript module, the <a href="https://spacetimedb.com/submodules/retry" target="_blank" rel="noopener noreferrer" class="">Retry submodule</a> retries background tasks with a limit on attempts, and waits twice as long before each new attempt.</li>
</ul>
