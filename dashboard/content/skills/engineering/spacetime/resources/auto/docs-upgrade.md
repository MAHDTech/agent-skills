from SpacetimeDB 1.0 to 2.0</h1></header>
<p>This guide covers the breaking changes between SpacetimeDB 1.0 and 2.0 and how to update your code.</p>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="overview-of-changes">Overview of Changes<a href="#overview-of-changes" class="hash-link" aria-label="Direct link to Overview of Changes" title="Direct link to Overview of Changes" translate="no">​</a></h2>
<p>SpacetimeDB 2.0 introduces a new WebSocket protocol (v2) and SDK with several breaking changes aimed at simplifying the programming model and improving security:</p>
\<ol\>
<li class=""><strong>Reducer callbacks removed</strong> -- replaced by event tables and per-call <code>_then()</code> callbacks</li>
<li class=""><strong><code>light_mode</code> removed</strong> -- no longer necessary since reducer events are no longer broadcast</li>
<li class=""><strong><code>CallReducerFlags</code> removed</strong> -- <code>NoSuccessNotify</code> and <code>set_reducer_flags()</code> are gone</li>
<li class=""><strong>Event tables introduced</strong> -- a new table type for publishing transient events to subscribers</li>
<li class=""><strong>Confirmed reads enabled by default</strong> -- subscription updates and SQL results are only sent after the transaction is confirmed durable</li>
</ol>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="reducer-callbacks">Reducer Callbacks<a href="#reducer-callbacks" class="hash-link" aria-label="Direct link to Reducer Callbacks" title="Direct link to Reducer Callbacks" translate="no">​</a></h2>

<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="why-event-tables-are-better">Why event tables are better<a href="#why-event-tables-are-better" class="hash-link" aria-label="Direct link to Why event tables are better" title="Direct link to Why event tables are better" translate="no">​</a></h3>
\<ul\>
<li class=""><strong>Security</strong>: You control exactly what data is published. In 1.0, reducer arguments were broadcast to any subscriber of affected rows, which could accidentally leak sensitive data.</li>
<li class=""><strong>Flexibility</strong>: Multiple reducers can insert the same event type. In 1.0, events were tied 1:1 to a specific reducer.</li>
<li class=""><strong>Transactional</strong>: Events are only published if the transaction commits. In 1.0, workarounds using scheduled reducers were not transactional.</li>
<li class=""><strong>Row-level security</strong>: RLS rules apply to event tables, so you can control which clients see which events.</li>
<li class=""><strong>Queryable</strong>: Event tables can be subscribed to with query builders (or SQL), and can be filtered per-client.</li>
</ul>
<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="event-table-details">Event table details<a href="#event-table-details" class="hash-link" aria-label="Direct link to Event table details" title="Direct link to Event table details" translate="no">​</a></h3>
\<ul\>
<li class="">Event tables are always empty outside of a transaction. They don&#x27;t accumulate rows.</li>
<li class="">On the client, <code>count()</code> always returns 0 and <code>iter()</code> is always empty.</li>
<li class="">Only <code>on_insert</code> callbacks are generated (no <code>on_delete</code> or <code>on_update</code>).</li>
<li class="">The <code>event</code> keyword in <code>#[table(..., event)]</code> marks the table as transient.</li>
<li class="">Event tables can be subscribed to with subscribe-all helpers or explicit typed queries, but clients observe them only through insert callbacks.</li>
</ul>

<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="table-name-canonicalization">Table Name Canonicalization<a href="#table-name-canonicalization" class="hash-link" aria-label="Direct link to Table Name Canonicalization" title="Direct link to Table Name Canonicalization" translate="no">​</a></h2>
<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="what-changed-2">What changed<a href="#what-changed-2" class="hash-link" aria-label="Direct link to What changed" title="Direct link to What changed" translate="no">​</a></h3>
<p>SpacetimeDB 2.0 no longer equates the canonical name of your tables and indexes with the accessor method you use in module or client code. The canonical name is largely an internal detail, but you may encounter it when making SQL queries, or in the migration plans printed by <code>spacetime publish</code>.</p>

<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="auto-migrating-existing-databases">Auto-migrating existing databases<a href="#auto-migrating-existing-databases" class="hash-link" aria-label="Direct link to Auto-migrating existing databases" title="Direct link to Auto-migrating existing databases" translate="no">​</a></h3>

<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="private-items-are-not-code-generated-by-default">Private Items Are Not Code-Generated By Default<a href="#private-items-are-not-code-generated-by-default" class="hash-link" aria-label="Direct link to Private Items Are Not Code-Generated By Default" title="Direct link to Private Items Are Not Code-Generated By Default" translate="no">​</a></h2>
<p>Starting in SpacetimeDB 2.0, <code>spacetime generate</code> will not generate bindings for private tables or functions by default. These bindings were confusing, as only clients authenticated as the database owner or a collaborator could access them, with most clients seeing an error when trying to subscribe to a private table or invoke a private function.</p>
<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="pass---include-private-to-spacetime-generate">Pass <code>--include-private</code> to <code>spacetime generate</code><a href="#pass---include-private-to-spacetime-generate" class="hash-link" aria-label="Direct link to pass---include-private-to-spacetime-generate" title="Direct link to pass---include-private-to-spacetime-generate" translate="no">​</a></h3>
<p>For clients which rely on generated bindings to private tables or functions, pass the <code>--include-private</code> flag to the <code>spacetime generate</code> CLI command.</p>

<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="confirmed-reads-enabled-by-default">Confirmed Reads Enabled by Default<a href="#confirmed-reads-enabled-by-default" class="hash-link" aria-label="Direct link to Confirmed Reads Enabled by Default" title="Direct link to Confirmed Reads Enabled by Default" translate="no">​</a></h2>
<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="what-changed-5">What changed<a href="#what-changed-5" class="hash-link" aria-label="Direct link to What changed" title="Direct link to What changed" translate="no">​</a></h3>
<p>In 1.0, subscription updates and SQL query results were sent to the client immediately, before the underlying transaction was confirmed to be durable. This meant a client could observe a row that was later lost if the server crashed before persisting it.</p>
<p>In 2.0, <strong>confirmed reads are enabled by default</strong>. The server waits until a transaction is confirmed durable before sending updates to clients. This ensures that any data a client receives will survive a server restart.</p>
<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="impact">Impact<a href="#impact" class="hash-link" aria-label="Direct link to Impact" title="Direct link to Impact" translate="no">​</a></h3>
\<ul\>
<li class=""><strong>Slightly higher latency</strong>: Subscription updates and SQL results may arrive a few milliseconds later, as the server waits for durability confirmation before sending them.</li>
<li class=""><strong>Stronger consistency</strong>: Clients will never observe data that could be lost due to a crash.</li>
<li class=""><strong>No code changes required</strong>: This is a server-side default change. Existing client code works without modification.</li>
</ul>

<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="quick-migration-checklist">Quick Migration Checklist<a href="#quick-migration-checklist" class="hash-link" aria-label="Direct link to Quick Migration Checklist" title="Direct link to Quick Migration Checklist" translate="no">​</a></h2>
<ul class="contains-task-list containsTaskList_AlET">
<li class="task-list-item"><input type="checkbox" disabled=""> <!-- -->Remove all <code>ctx.reducers.on_\<reducer\>()</code> calls<!-- -->
\<ul\>
<li class="">Replace with <code>_then()</code> callbacks for your own reducer calls</li>
<li class="">Unreal: replace with generated <code>On\<Reducer\></code> delegates on the calling connection</li>
<li class="">Replace with event tables + <code>on_insert</code> for cross-client notifications</li>
</ul>
</li>
<li class="task-list-item"><input type="checkbox" disabled=""> <!-- -->Migrate Unreal subscription SQL strings to typed queries where appropriate<!-- -->
\<ul\>
<li class="">Use <code>Conn->SubscriptionBuilder()->AddQuery(...)->Subscribe()</code> instead of <code>Subscribe({ TEXT("SELECT ...") })</code></li>
</ul>
</li>
<li class="task-list-item"><input type="checkbox" disabled=""> <!-- -->Update <code>Event::UnknownTransaction</code> matches to <code>Event::Transaction</code></li>
<li class="task-list-item"><input type="checkbox" disabled=""> <!-- -->For each reducer whose args you were observing from other clients:<!-- -->
\<ol\>
<li class="">Create an <code>#[table(..., event)]</code> on the server</li>
<li class="">Insert into it from the reducer</li>
<li class="">Subscribe to it on the client</li>
<li class="">Use <code>on_insert</code> instead of the old reducer callback</li>
</ol>
</li>
<li class="task-list-item"><input type="checkbox" disabled=""> <!-- -->Replace <code>name =</code> with <code>accessor =</code> in table and index definitions</li>
<li class="task-list-item"><input type="checkbox" disabled=""> <strong>TypeScript:</strong> Use <code>schema({ table })</code> or <code>schema({ t1, t2 })</code> — never <code>schema(table)</code> or <code>schema(t1, t2, t3)</code></li>
<li class="task-list-item"><input type="checkbox" disabled=""> <!-- -->Set your module&#x27;s case conversion policy to <code>None</code></li>
<li class="task-list-item"><input type="checkbox" disabled=""> <!-- -->Change <code>with_module_name</code> to <code>with_database_name</code></li>
<li class="task-list-item"><input type="checkbox" disabled=""> <!-- -->Change <code>ctx.sender</code> to <code>ctx.sender()</code>
\<ul\>
<li class="">Only necessary in Rust and C++ modules.</li>
</ul>
</li>
<li class="task-list-item"><input type="checkbox" disabled=""> <!-- -->Remove <code>update</code> calls on non-primary key unique indexes<!-- -->
\<ul\>
<li class="">When leaving the primary key value unchanged, update using the primary key index</li>
<li class="">When altering the primary key value, delete and insert</li>
</ul>
</li>
<li class="task-list-item"><input type="checkbox" disabled=""> <!-- -->Remove superfluous auth logic from scheduled functions which are not called by clients</li>
<li class="task-list-item"><input type="checkbox" disabled=""> <!-- -->Define wrappers around scheduled functions which are called by clients</li>
<li class="task-list-item"><input type="checkbox" disabled=""> <!-- -->Use <code>spacetime generate --include-private</code> if you rely on bindings for private tables or functions</li>
<li class="task-list-item"><input type="checkbox" disabled=""> <!-- -->Remove <code>with_light_mode()</code> from <code>DbConnectionBuilder</code>
\<ul\>
<li class="">Unreal: no action if you are already on the 2.0 Unreal SDK; there is no public <code>WithLightMode(...)</code></li>
</ul>
</li>
<li class="task-list-item"><input type="checkbox" disabled=""> <!-- -->Remove <code>set_reducer_flags()</code> calls and <code>CallReducerFlags</code> imports<!-- -->
\<ul\>
<li class="">Unreal: no action if you are already on the 2.0 Unreal SDK; there is no public reducer-flags API</li>
</ul>
</li>
