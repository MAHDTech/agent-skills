<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="how-subscriptions-work">How Subscriptions Work<a href="#how-subscriptions-work" class="hash-link" aria-label="Direct link to How Subscriptions Work" title="Direct link to How Subscriptions Work" translate="no">​</a></h2>
\<ol\>
<li class=""><strong>Subscribe</strong>: Subscribe with queries to the data you need</li>
<li class=""><strong>Receive initial data</strong>: SpacetimeDB sends all matching rows immediately</li>
<li class=""><strong>Receive updates</strong>: When subscribed rows change, you get real-time updates</li>
<li class=""><strong>React to changes</strong>: Use row callbacks (<code>onInsert</code>, <code>onDelete</code>, <code>onUpdate</code>) to handle changes</li>
</ol>
<p>The client maintains a local cache of subscribed data. Reading from the cache is instant since it&#x27;s local memory.</p>
<p>For advanced raw SQL subscription syntax, see the <a class="" href="/docs/reference/sql#subscriptions">SQL docs</a>.</p>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="common-api-concepts">Common API Concepts<a href="#common-api-concepts" class="hash-link" aria-label="Direct link to Common API Concepts" title="Direct link to Common API Concepts" translate="no">​</a></h2>
<p>This page focuses on subscription behavior and usage patterns that apply across SDKs. For exact method signatures and SDK-specific overloads, use the language references.</p>
<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="builder-and-lifecycle-callbacks">Builder and Lifecycle Callbacks<a href="#builder-and-lifecycle-callbacks" class="hash-link" aria-label="Direct link to Builder and Lifecycle Callbacks" title="Direct link to Builder and Lifecycle Callbacks" translate="no">​</a></h3>
<p>All SDKs expose a builder API for creating subscriptions:</p>
\<ul\>
<li class="">Register an applied callback: runs once initial matching rows are present in the local cache.</li>
<li class="">Register an error callback: runs if subscription registration fails or a subscription later terminates with an error.</li>
<li class="">Subscribe with one or more queries.</li>
</ul>
<p>In Unreal, inspect the initial subscribed data set in <code>OnApplied</code>. Use table callbacks like <code>OnInsert</code>, <code>OnDelete</code>, and <code>OnUpdate</code> for later live changes.</p>
<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="query-forms">Query Forms<a href="#query-forms" class="hash-link" aria-label="Direct link to Query Forms" title="Direct link to Query Forms" translate="no">​</a></h3>
<p>All SDKs support subscriptions. Query builders are the recommended default across SDKs, with raw SQL available where needed:</p>
<table><thead><tr><th>SDK</th><th>Typed Query Builder Support</th><th>Entry Point</th></tr></thead>\<tbody\><tr><td>TypeScript</td><td>Yes</td><td><code>tables.<table>.where(...)</code> passed to <code>subscribe(...)</code></td></tr><tr><td>C#</td><td>Yes</td><td><code>SubscriptionBuilder.AddQuery(...).Subscribe()</code></td></tr><tr><td>Rust</td><td>Yes</td><td><code>subscription_builder().add_query(...).subscribe()</code></td></tr><tr><td>Unreal</td><td>Yes</td><td><code>SubscriptionBuilder.AddQuery(...).Subscribe()</code></td></tr></tbody></table>
<p>Unreal also supports raw SQL subscriptions through <code>Subscribe(const TArray\<FString\>& SQL)</code> when you need direct SQL control.</p>
<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="subscription-handles">Subscription Handles<a href="#subscription-handles" class="hash-link" aria-label="Direct link to Subscription Handles" title="Direct link to Subscription Handles" translate="no">​</a></h3>
<p>Subscribing returns a handle that manages an individual subscription lifecycle.</p>
\<ul\>
<li class=""><code>isActive</code> / <code>IsActive</code> / <code>is_active</code> indicates that matching rows are currently active in the cache.</li>
<li class=""><code>isEnded</code> / <code>IsEnded</code> / <code>is_ended</code> indicates a subscription has ended, either from unsubscribe or error.</li>
<li class="">Unsubscribe is asynchronous: rows are removed after the unsubscribe operation is applied.</li>
<li class=""><code>subscribeToAllTables</code> / <code>SubscribeToAllTables</code> / <code>subscribe_to_all_tables</code> is a convenience entry point intended for simple clients and is not individually cancelable.</li>
</ul>

<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="1-writing-efficient-subscription-queries">1. Writing Efficient Subscription Queries<a href="#1-writing-efficient-subscription-queries" class="hash-link" aria-label="Direct link to 1. <p>Use the typed query builder to express precise filters and keep subscriptions small. If you use raw SQL subscriptions, see <a class="" href="/docs/reference/sql#best-practices-for-performance-and-scalability">SQL Best Practices</a>.</p>
<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="2-group-subscriptions-with-the-same-lifetime-together">2. Group Subscriptions with the Same Lifetime Together<a href="#2-group-subscriptions-with-the-same-lifetime-together" class="hash-link" aria-label="Direct link to 2. Group Subscriptions with the Same Lifetime Together" title="Direct link to 2. Group Subscriptions with the Same Lifetime Together" translate="no">​</a></h3>
<p>Subscriptions with the same lifetime should be grouped together.</p>
<p>For example, you may have certain data that is required for the lifetime of your application,
but you may have other data that is only sometimes required by your application.</p>
<p>By managing these sets as two independent subscriptions,
your application can subscribe and unsubscribe from the latter,
without needlessly unsubscribing and resubscribing to the former.</p>
<p>This will improve throughput by reducing the amount of data transferred from the database to your application.</p>

<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="3-subscribe-before-unsubscribing">3. Subscribe Before Unsubscribing<a href="#3-subscribe-before-unsubscribing" class="hash-link" aria-label="Direct link to 3. Subscribe Before Unsubscribing" title="Direct link to 3. Subscribe Before Unsubscribing" translate="no">​</a></h3>
<p>If you want to update or modify a subscription by dropping it and subscribing to a new set,
you should subscribe to the new set before unsubscribing from the old one.</p>
<p>This is because SpacetimeDB subscriptions are zero-copy.
Subscribing to the same query more than once doesn&#x27;t incur additional processing or serialization overhead.
Likewise, if a query is subscribed to more than once,
unsubscribing from it does not result in any server processing or data serializtion.</p>

<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="4-avoid-overlapping-queries">4. Avoid Overlapping Queries<a href="#4-avoid-overlapping-queries" class="hash-link" aria-label="Direct link to 4. Avoid Overlapping Queries" title="Direct link to 4. Avoid Overlapping Queries" translate="no">​</a></h3>
<p>This refers to distinct queries that return intersecting data sets,
which can result in the server processing and serializing the same row multiple times.
While SpacetimeDB can manage this redundancy, it may lead to unnecessary inefficiencies.</p>
<p>Consider the following two query builder subscriptions:</p>
<pre tabindex="0" class="codeBlockStandalone_LlrK thin-scrollbar codeBlockContainer_hFbQ theme-code-block" style="--prism-color:#bfc7d5;--prism-background-color:#292d3e"><code class="codeBlockLines_JqGU"><span class="line"><span style="color:#F8F8F2">tables.user</span></span>
<span class="line"><span style="color:#F8F8F2">tables.user.</span><span style="color:#50FA7B">where</span><span style="color:#F8F8F2">(</span><span style="color:#FFB86C;font-style:italic">r</span><span style="color:#FF79C6"> =></span><span style="color:#F8F8F2"> r.id.</span><span style="color:#50FA7B">eq</span><span style="color:#F8F8F2">(</span><span style="color:#BD93F9">5</span><span style="color:#F8F8F2">))</span></span></code></pre>
<p>If <code>User.id</code> is a unique or primary key column,
the cost of subscribing to both queries is minimal.
This is because the server will use an index when processing the 2nd query,
and it will only serialize a single row for the 2nd query.</p>
<p>In contrast, consider these two query builder subscriptions:</p>
<pre tabindex="0" class="codeBlockStandalone_LlrK thin-scrollbar codeBlockContainer_hFbQ theme-code-block" style="--prism-color:#bfc7d5;--prism-background-color:#292d3e"><code class="codeBlockLines_JqGU"><span class="line"><span style="color:#F8F8F2">tables.user</span></span>
<span class="line"><span style="color:#F8F8F2">tables.user.</span><span style="color:#50FA7B">where</span><span style="color:#F8F8F2">(</span><span style="color:#FFB86C;font-style:italic">r</span><span style="color:#FF79C6"> =></span><span style="color:#F8F8F2"> r.id.</span><span style="color:#50FA7B">ne</span><span style="color:#F8F8F2">(</span><span style="color:#BD93F9">5</span><span style="color:#F8F8F2">))</span></span></code></pre>
<p>The server must now process each row of the <code>User</code> table twice,
since the 2nd query cannot be processed using an index.
It must also serialize all but one row of the <code>User</code> table twice,
due to the significant overlap between the two queries.</p>
<p>By following these best practices, you can optimize your data replication strategy and ensure your application remains efficient and responsive.</p></div><footer class="theme-doc-footer
