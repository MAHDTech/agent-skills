markdown">\<header\>\<h1\>Event Tables</h1></header><p>In many applications, particularly games and real-time systems, modules need to notify clients about things that happened without storing that information permanently. A combat system might need to tell clients "entity X took 50 damage" so they can display a floating damage number, but there is no reason to keep that record in the database after the moment has passed.</p>
<p>Event tables provide exactly this capability. An event table is a table whose rows are inserted and then immediately deleted by the database: they exist only for the duration of the transaction that created them. When the transaction commits, the rows are broadcast to subscribed clients and then deleted from the table. Between transactions, the table is always empty.</p>
<p>From the module&#x27;s perspective, event tables behave like regular tables during a reducer&#x27;s execution. You insert rows, query them, and apply constraints just as you would with any other table. The difference is purely in what happens after the transaction completes: rather than merging the rows into the committed database state, SpacetimeDB publishes them to subscribers and deletes them from the table. The inserts are still recorded in the commitlog, so a full history of events is preserved.</p>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="defining-an-event-table">Defining an Event Table<a href="#defining-an-event-table" class="hash-link" aria-label="Direct link to Defining an Event Table" title="Direct link to Defining an Event Table" translate="no">​</a></h2>
<p>To declare a table as an event table, add the <code>event</code> attribute to the table definition. Event tables support all the same column types, constraints, indexes, and auto-increment fields as regular tables.</p>

<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="publishing-events">Publishing Events<a href="#publishing-events" class="hash-link" aria-label="Direct link to Publishing Events" title="Direct link to Publishing Events" translate="no">​</a></h2>
<p>To publish an event, simply insert a row into the event table from within a reducer. The insertion works exactly like inserting into a regular table. The row is visible within the current transaction and can be queried or used in constraints. When the transaction commits successfully, the row is broadcast to all subscribed clients. If the reducer panics or the transaction is rolled back, no events are sent.</p>

<p>Because events are just table inserts, you can publish the same event type from any number of reducers. A <code>DamageEvent</code> might be inserted by a melee attack reducer, a spell reducer, and an environmental hazard reducer and clients receive the same event regardless of what triggered it.</p>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="constraints-and-indexes">Constraints and Indexes<a href="#constraints-and-indexes" class="hash-link" aria-label="Direct link to Constraints and Indexes" title="Direct link to Constraints and Indexes" translate="no">​</a></h2>
<p>Primary keys, unique constraints, indexes, sequences, and auto-increment columns all work on event tables. The key difference is that these constraints are enforced only within a single transaction and reset between transactions.</p>
<p>For example, if an event table has a primary key column, inserting two rows with the same primary key within the same transaction will produce an error, just as it would for a regular table. However, inserting a row with primary key <code>1</code> in one transaction and another row with primary key <code>1</code> in a later transaction will both succeed, because the table is empty at the start of each transaction.</p>
<p>This behavior follows naturally from the fact that event table rows are never merged into the committed state. Each transaction begins with an empty table.</p>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="subscribing-to-events">Subscribing to Events<a href="#subscribing-to-events" class="hash-link" aria-label="Direct link to Subscribing to Events" title="Direct link to Subscribing to Events" translate="no">​</a></h2>
<p>On the client side, event tables are subscribed to like regular tables: either through subscribe-all helpers such as <code>subscribeToAllTables</code>, <code>SubscribeToAllTables</code>, and <code>subscribe_to_all_tables</code>, or through explicit typed queries. Once subscribed, event table rows are never stored in the client cache. Calling <code>count()</code> on an event table always returns 0, and <code>iter()</code> always yields no rows. Instead, you observe events through <code>on_insert</code> callbacks, which fire for each row that was inserted during the transaction.</p>
<p>Because event table rows are ephemeral, only <code>on_insert</code> callbacks are available. There are no <code>on_delete</code>, <code>on_update</code>, or <code>on_before_delete</code> callbacks, since rows are never present in the client state to be deleted or updated.</p>

<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="how-it-works">How It Works<a href="#how-it-works" class="hash-link" aria-label="Direct link to How It Works" title="Direct link to How It Works" translate="no">​</a></h2>
<p>Conceptually, every insert into an event table is a <strong>noop</strong>: an insert paired with an automatic delete. The result is that the table state never changes; it is always the empty set. This model has several consequences for how SpacetimeDB handles event tables internally.</p>
<p><strong>Wire format.</strong> Event tables require the v2 WebSocket protocol. Clients connected via the v1 protocol that attempt to subscribe to an event table will receive an error message directing them to upgrade.</p>
<div class="theme-admonition theme-admonition-tip admonition_Ph9R alert alert--success"><div class="admonitionHeading_kG9t"><span class="admonitionIcon_VA_f"><svg viewBox="0 0 12 16"><path fill-rule="evenodd" d="M6.5 0C3.48 0 1 2.19 1 5c0 .92.55 2.25 1 3 1.34 2.25 1.78 2.78 2 4v1h5v-1c.22-1.22.66-1.75 2-4 .45-.75 1-2.08 1-3 0-2.81-2.48-5-5.5-5zm3.64 7.48c-.25.44-.47.8-.67 1.11-.86 1.41-1.25 2.06-1.45 3.23-.02.05-.02.11-.02.17H5c0-.06 0-.13-.02-.17-.2-1.17-.59-1.83-1.45-3.23-.2-.31-.42-.67-.67-1.11C2.44 6.78 2 5.65 2 5c0-2.2 2.02-4 4.5-4 1.22 0 2.36.42 3.22 1.19C10.55 2.94 11 3.94 11 5c0 .66-.44 1.78-.86 2.48zM4 14h5c-.23 1.14-1.3 2-2.5 2s-2.27-.86-2.5-2z"></path></svg></span>Migrating from reducer callbacks</div><div class="admonitionContent_STxx"><p>If you previously used <code>ctx.reducers.on_\<reducer_name\>()</code> callbacks to receive transient data, event tables are the recommended replacement. Define an event table with the fields you want to publish, insert a row in your reducer, and register an <code>on_insert</code> callback on the client via <code>ctx.db.\<event_table\>().on_insert(...)</code>. See the <a class="" href="/docs/upgrade">migration guide</a> for details.</p></div></div>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="row-level-security">Row-Level Security<a href="#row-level-security" class="hash-link" aria-label="Direct link to Row-Level Security" title="Direct link to Row-Level Security" translate="no">​</a></h2>
<p>Row-level security applies to event tables with the same semantics as regular tables. This means you can use RLS rules to control which clients receive which events based on their identity. For example, you could restrict a <code>DamageEvent</code> so that only clients whose identity matches the <code>entity_id</code> field receive the event, preventing players from seeing damage dealt to other players.</p>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="current-limitations">Current Limitations<a href="#current-limitations" class="hash-link" aria-label="Direct link to Current Limitations" title="Direct link to Current Limitations" translate="no">​</a></h2>
<p>Event tables are fully functional for the use cases described above, but a few capabilities are intentionally restricted for the initial release:</p>
\<ul\>
<li class=""><strong>Subscription joins.</strong> Event tables cannot currently be used as the lookup (right/inner) table in a subscription join. While this is well-defined (the noop semantics make joined results behave as event tables too), it is restricted for ease of implementation and will be relaxed in a future release.</li>
<li class=""><strong>Views.</strong> Event tables cannot currently be accessed within view functions. Although the proposal defines clear semantics for this (event-table-ness is "infectious," meaning a view that joins on an event table itself becomes an event table), this is deferred to a future release.</li>
</ul>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="use-cases">Use Cases<a href="#use-cases" class="hash-link" aria-label="Direct link to Use Cases" title="Direct link to Use Cases" translate="no">​</a></h2>
<p>Event tables are well-suited to any situation where the module needs to notify clients about something that happened without storing a permanent record:</p>
\<ul\>
<li class=""><strong>Combat and damage events.</strong> Floating damage numbers, hit indicators, and kill notifications.</li>
<li class=""><strong>Chat messages.</strong> Real-time chat where messages are displayed on arrival but don&#x27;t need server-side persistence.</li>
<li class=""><strong>Notifications.</strong> Transient UI messages like "Player joined", "Achievement unlocked", or "Trade completed".</li>
<li class=""><strong>Sound and visual effects.</strong> Triggering client-side effects such as explosions, particles, or audio cues at the right moment.</li>
<li class=""><strong>Telemetry and debugging.</strong> Streaming diagnostic data to a connected developer client without accumulating it in the database.</li>
</ul>
