id="host">Host<a href="#host" class="hash-link" aria-label="Direct link to Host" title="Direct link to Host" translate="no">​</a></h2>
<p>A SpacetimeDB <strong>host</strong> is a server that hosts <a href="#database" class="">databases</a>. You can run your own host, or use the SpacetimeDB maincloud. Many databases can run on a single host.</p>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="database">Database<a href="#database" class="hash-link" aria-label="Direct link to Database" title="Direct link to Database" translate="no">​</a></h2>
<p>A SpacetimeDB <strong>database</strong> is an application that runs on a <a href="#host" class="">host</a>.</p>
<p>A database exports <a href="#table" class="">tables</a>, which store data, and <a href="#reducer" class="">reducers</a>, which allow <a href="#client" class="">clients</a> to make requests.</p>
<p>A database&#x27;s schema and business logic is specified by a piece of software called a <strong>module</strong>. Modules can be written in C#, C++, Rust or TypeScript.</p>
<p>(Technically, a SpacetimeDB module is a <a href="https://developer.mozilla.org/en-US/docs/WebAssembly" target="_blank" rel="noopener noreferrer" class="">WebAssembly module</a> or JavaScript bundle, that imports a specific low-level <a class="" href="/docs/webassembly-abi">WebAssembly ABI</a> and exports a small number of special functions. However, the SpacetimeDB <a class="" href="/docs/databases">server-side libraries</a> hide these low-level details. As a developer, writing a module is mostly like writing any other application, except for the fact that a <a href="https://spacetimedb.com/install" target="_blank" rel="noopener noreferrer" class="">special CLI tool</a> is used to deploy the application.)</p>

<p>These look mostly like regular function calls, but under the hood,
the client sends a request over the internet, which the database processes and responds to.</p>
<p>The <code>ReducerContext</code> is a reducer&#x27;s only mandatory parameter
and includes information about the caller&#x27;s <a href="#identity" class="">identity</a>.
This can be used to authenticate the caller.</p>
<p>Reducers are run in their own separate and atomic <a href="https://en.wikipedia.org/wiki/Database_transaction" target="_blank" rel="noopener noreferrer" class="">database transactions</a>.
When a reducer completes successfully, the changes the reducer has made,
such as inserting a table row, are <em>committed</em> to the database.
However, if the reducer instead returns an error, or throws an exception,
the database will instead reject the request and <em>revert</em> all those changes.
That is, reducers and transactions are all-or-nothing requests.
It&#x27;s not possible to keep the first half of a reducer&#x27;s changes and discard the last.</p>
<p>Transactions are only started by requests from outside the database.
When a reducer calls another reducer directly, as in the example below,
the changes in the called reducer does not happen in its own child transaction.
Instead, when the nested reducer gracefully errors,
and the overall reducer completes successfully,
the changes in the nested one are still persisted.</p>

<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="procedure">Procedure<a href="#procedure" class="hash-link" aria-label="Direct link to Procedure" title="Direct link to Procedure" translate="no">​</a></h2>
<p>A <strong>procedure</strong> is a function exported by a <a href="#database" class="">database</a>, similar to a <a href="#reducer" class="">reducer</a>.
Connected <a href="#client" class="">clients</a> can call procedures.
Procedures can perform additional operations not possible in reducers, including making HTTP requests to external services.
However, procedures don&#x27;t automatically run in database transactions,
and must manually open and commit a transaction in order to read from or modify the database state.</p>

<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="view">View<a href="#view" class="hash-link" aria-label="Direct link to View" title="Direct link to View" translate="no">​</a></h2>
<p>A <strong>view</strong> is a read-only function exported by a <a href="#database" class="">database</a> that computes and returns results from tables. Unlike <a href="#reducer" class="">reducers</a>, views do not modify database state - they only query and return data. Views are useful for computing derived data, aggregations, or joining multiple tables before sending results to clients.</p>
<p>Views must be declared as <code>public</code> and accept only a context parameter. They can return either a single row or multiple rows. Like tables, views can be subscribed to and automatically update when their underlying data changes.</p>

<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="client">Client<a href="#client" class="hash-link" aria-label="Direct link to Client" title="Direct link to Client" translate="no">​</a></h2>
<p>A <strong>client</strong> is an application that connects to a <a href="#database" class="">database</a>. A client logs in using an <a href="#identity" class="">identity</a> and receives an <a href="#connectionid" class="">connection id</a> to identify the connection. After that, it can call <a href="#reducer" class="">reducers</a> and query public <a href="#table" class="">tables</a>.</p>
<p>Clients are written using the <a class="" href="/docs/clients">client-side SDKs</a>. The <code>spacetime</code> CLI tool allows automatically generating code that works with the client-side SDKs to talk to a particular database. The client SDKs internally maintain a long-lived streaming connection to SpacetimeDB, allowing high-performance real-time interactions.</p>
<p>Clients are regular software applications that developers can choose how to deploy (through Steam, app stores, package managers, or any other software deployment method, depending on the needs of the application.)</p>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="identity">Identity<a href="#identity" class="hash-link" aria-label="Direct link to Identity" title="Direct link to Identity" translate="no">​</a></h2>
<p>A SpacetimeDB <code>Identity</code> identifies someone interacting with a database. It is a long lived, public, globally valid identifier that will always refer to the same end user, even across different connections.</p>
<p>A user&#x27;s <code>Identity</code> is attached to every <a href="#reducer" class="">reducer call</a> they make, and you can use this to decide what they are allowed to do.</p>
<p>Modules themselves also have Identities. When you <code>spacetime publish</code> a module, it will automatically be issued an <code>Identity</code> to distinguish it from other modules. Your client application will need to provide this <code>Identity</code> when connecting to the <a href="#host" class="">host</a>.</p>
<p>Identities are issued using the <a href="https://openid.net/developers/how-connect-works/" target="_blank" rel="noopener noreferrer" class="">OpenID Connect</a> specification. Database developers are responsible for issuing Identities to their end users. OpenID Connect lets users log in to these accounts through standard services like Google and Facebook.</p>

<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="connectionid">ConnectionId<a href="#connectionid" class="hash-link" aria-label="Direct link to ConnectionId" title="Direct link to ConnectionId" translate="no">​</a></h2>
<p>A <code>ConnectionId</code> identifies client connections to a SpacetimeDB database.</p>
<p>A user has a single <a href="#identity" class=""><code>Identity</code></a>, but may open multiple connections to your database. Each of these will receive a unique <code>ConnectionId</code>.</p>
