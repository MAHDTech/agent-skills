page</button></div><div class="theme-doc-markdown markdown">\<header\>\<h1\>Transactions and Atomicity</h1></header><p>SpacetimeDB provides strong transactional guarantees for all database operations. Every <a class="" href="/docs/functions/reducers">reducer</a> runs inside a database transaction, ensuring your data remains consistent and reliable even under concurrent load.</p>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="what-is-a-transaction">What is a Transaction?<a href="#what-is-a-transaction" class="hash-link" aria-label="Direct link to What is a Transaction?" title="Direct link to What is a Transaction?" translate="no">​</a></h2>
<p>A <a href="https://en.wikipedia.org/wiki/Database_transaction" target="_blank" rel="noopener noreferrer" class="">database transaction</a> is a sequence of operations that execute as a single, indivisible unit of work. In SpacetimeDB, each reducer invocation is a transaction - either all of its changes succeed and are committed to the database, or all changes are rolled back as if the reducer never ran.</p>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="acid-properties">ACID Properties<a href="#acid-properties" class="hash-link" aria-label="Direct link to ACID Properties" title="Direct link to ACID Properties" translate="no">​</a></h2>
<p>SpacetimeDB transactions provide the following guarantees:</p>
<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="atomicity">Atomicity<a href="#atomicity" class="hash-link" aria-label="Direct link to Atomicity" title="Direct link to Atomicity" translate="no">​</a></h3>
<p><strong>All-or-nothing execution</strong>: A reducer&#x27;s changes either all succeed or all fail together. There&#x27;s no partial state.</p>
\<ul\>
<li class="">If a reducer completes successfully, all changes (inserts, updates, deletes) are <strong>committed</strong> to the database</li>
<li class="">If a reducer throws an exception or returns an error, all changes are <strong>rolled back</strong> and the database remains unchanged</li>
<li class="">It&#x27;s not possible to keep some changes and discard others from a single reducer execution</li>
</ul>
<div class="theme-admonition theme-admonition-note admonition_Ph9R alert alert--secondary"><div class="admonitionHeading_kG9t"><span class="admonitionIcon_VA_f"><svg viewBox="0 0 14 16"><path fill-rule="evenodd" d="M6.3 5.69a.942.942 0 0 1-.28-.7c0-.28.09-.52.28-.7.19-.18.42-.28.7-.28.28 0 .52.09.7.28.18.19.28.42.28.7 0 .28-.09.52-.28.7a1 1 0 0 1-.7.3c-.28 0-.52-.11-.7-.3zM8 7.99c-.02-.25-.11-.48-.31-.69-.2-.19-.42-.3-.69-.31H6c-.27.02-.48.13-.69.31-.2.2-.3.44-.31.69h1v3c.02.27.11.5.31.69.2.2.42.31.69.31h1c.27 0 .48-.11.69-.31.2-.19.3-.42.31-.69H8V7.98v.01zM7 2.3c-3.14 0-5.7 2.54-5.7 5.68 0 3.14 2.56 5.7 5.7 5.7s5.7-2.55 5.7-5.7c0-3.15-2.56-5.69-5.7-5.69v.01zM7 .98c3.86 0 7 3.14 7 7s-3.14 7-7 7-7-3.12-7-7 3.14-7 7-7z"></path></svg></span>note</div><div class="admonitionContent_STxx"><p>This atomicity guarantee applies to <strong>reducers</strong>, which run in a single transaction. <a class="" href="/docs/functions/procedures">Procedures</a> can manually open multiple separate transactions, where each transaction is individually atomic, but the procedure as a whole is not. See <a href="#procedures-manual-transactions" class="">Procedures: Manual Transactions</a> below.</p></div></div>
<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="consistency">Consistency<a href="#consistency" class="hash-link" aria-label="Direct link to Consistency" title="Direct link to Consistency" translate="no">​</a></h3>
<p><strong>Valid states only</strong>: Transactions ensure the database moves from one valid state to another. All constraints (unique keys, indexes, foreign key-like relationships in your logic) are enforced.</p>
\<ul\>
<li class="">Unique constraints are checked before commit</li>
<li class="">If a constraint would be violated, the entire transaction is rolled back</li>
<li class="">The database never enters an invalid state</li>
</ul>
<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="isolation">Isolation<a href="#isolation" class="hash-link" aria-label="Direct link to Isolation" title="Direct link to Isolation" translate="no">​</a></h3>
<p><strong>Consistent snapshots</strong>: Each reducer sees a consistent snapshot of the database and doesn&#x27;t observe partial changes from other reducer executions.</p>
\<ul\>
<li class="">A reducer sees the database state as it was at the start of its transaction</li>
<li class="">A reducer will not observe the effects of other reducers modifying the database while it runs</li>
<li class="">Each reducer completes fully before its changes are visible to others</li>
</ul>
<p>This prevents race conditions and ensures predictable behavior.</p>
<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="durability">Durability<a href="#durability" class="hash-link" aria-label="Direct link to Durability" title="Direct link to Durability" translate="no">​</a></h3>
<p><strong>Persistent changes</strong>: Once a reducer successfully commits, its changes are permanent and will survive server restarts. SpacetimeDB persists committed transactions to disk.</p>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="transaction-scope">Transaction Scope<a href="#transaction-scope" class="hash-link" aria-label="Direct link to Transaction Scope" title="Direct link to Transaction Scope" translate="no">​</a></h2>
<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="reducers-automatic-transactions">Reducers: Automatic Transactions<a href="#reducers-automatic-transactions" class="hash-link" aria-label="Direct link to Reducers: Automatic Transactions" title="Direct link to Reducers: Automatic Transactions" translate="no">​</a></h3>
<p>Every reducer invocation automatically runs in its own transaction:</p>
\<ul\>
<li class="">The transaction starts when the reducer is called</li>
<li class="">The transaction commits when the reducer returns successfully</li>
<li class="">The transaction rolls back if the reducer throws an exception or returns an error</li>
</ul>
<p>You don&#x27;t need to manually start or commit transactions in reducers - SpacetimeDB handles this automatically.</p>
<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="nested-reducer-calls">Nested Reducer Calls<a href="#nested-reducer-calls" class="hash-link" aria-label="Direct link to Nested Reducer Calls" title="Direct link to Nested Reducer Calls" translate="no">​</a></h3>
<p>When a reducer calls another reducer directly (not via scheduling), they execute in the <strong>same transaction</strong>:</p>

<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="procedures-manual-transactions">Procedures: Manual Transactions<a href="#procedures-manual-transactions" class="hash-link" aria-label="Direct link to Procedures: Manual Transactions" title="Direct link to Procedures: Manual Transactions" translate="no">​</a></h3>
<p>Unlike reducers, <a class="" href="/docs/functions/procedures">procedures</a> don&#x27;t automatically run in transactions. Procedures can run transactions, but must manually open them using <code>with_tx</code> (Rust) or <code>withTx</code> (TypeScript). This gives procedures more flexibility:</p>
\<ul\>
<li class="">Procedures can perform operations <strong>outside</strong> transactions (like HTTP requests)</li>
<li class="">Procedures can open <strong>multiple separate transactions</strong> if needed</li>
<li class="">Each <code>with_tx</code>/<code>withTx</code> call creates a new transaction that commits independently</li>
</ul>
<p>See <a class="" href="/docs/functions/procedures">Procedures</a> for more details on manual transaction management.</p>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="best-practices">Best Practices<a href="#best-practices" class="hash-link" aria-label="Direct link to Best Practices" title="Direct link to Best Practices" translate="no">​</a></h2>
<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="keep-transactions-short">Keep Transactions Short<a href="#keep-transactions-short" class="hash-link" aria-label="Direct link to Keep Transactions Short" title="Direct link to Keep Transactions Short" translate="no">​</a></h3>
\<ul\>
<li class="">Perform only necessary database operations within reducers</li>
<li class="">Move external I/O (HTTP requests, etc.) to <a class="" href="/docs/functions/procedures">procedures</a></li>
<li class="">Shorter transactions reduce contention and improve throughput</li>
</ul>
<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="handle-errors-gracefully">Handle Errors Gracefully<a href="#handle-errors-gracefully" class="hash-link" aria-label="Direct link to Handle Errors Gracefully" title="Direct link to Handle Errors Gracefully" translate="no">​</a></h3>
\<ul\>
<li class="">Return descriptive errors to help clients understand failures</li>
<li class="">Use <code>Result<(), String></code> in Rust or throw exceptions with clear messages</li>
<li class="">Remember: any error rolls back ALL changes</li>
</ul>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="limitations">Limitations<a href="#limitations" class="hash-link" aria-label="Direct link to Limitations" title="Direct link to Limitations" translate="no">​</a></h2>
<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="no-nested-transactions">No Nested Transactions<a href="#no-nested-transactions" class="hash-link" aria-label="Direct link to No Nested Transactions" title="Direct link to No Nested Transactions" translate="no">​</a></h3>
<p>SpacetimeDB does not support nested transactions. When one reducer calls another, they share the same transaction. If you need separate transactions, use <a class="" href="/docs/tables/schedule-tables">scheduled reducers</a> to trigger the second reducer asynchronously.</p>
<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="auto-increment-is-not-transactional">Auto-Increment is Not Transactional<a href="#auto-increment-is-not-transactional" class="hash-link" aria-label="Direct link to Auto-Increment is Not Transactional" title="Direct link to Auto-Increment is Not Transactional" translate="no">​</a></h3>
<p>The <code>#[auto_inc]</code> sequence generator is not transactional:</p>
\<ul\>
<li class="">Sequence numbers are allocated even if a transaction rolls back</li>
<li class="">This can create gaps in your sequence</li>
