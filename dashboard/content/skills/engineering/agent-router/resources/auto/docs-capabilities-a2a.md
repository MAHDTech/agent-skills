<h2 class="anchor anchorTargetStickyNavbar_Vzrq" id="what-you-get">What you get<a href="#what-you-get" class="hash-link" aria-label="Direct link to What you get" title="Direct link to What you get" translate="no">​</a></h2>
<p>Following this page, an A2A agent behind the gateway gets:</p>
\<ul\>
<li class=""><strong>Routing</strong> for the agent card (<code>GET /.well-known/agent-card.json</code>) and the JSON-RPC endpoint, with hostnames, timeouts long enough for Server-Sent Events, and optional path rewriting.</li>
<li class=""><strong>Protocol validation</strong> by Envoy&#x27;s A2A filter: every POST on the route must be a JSON-RPC 2.0 envelope, and oversized bodies are rejected.</li>
<li class=""><strong>A2A fields in access logs and metrics</strong>: the JSON-RPC <code>method</code> and <code>id</code> (and, for A2A 0.3 clients, task and context IDs) land in Envoy dynamic metadata; the filter also exposes <code>a2a.requests_rejected</code>, <code>a2a.invalid_json</code> and <code>a2a.body_too_large</code> counters.</li>
<li class=""><strong>Client authentication</strong> (JWT, API key, external auth) on the RPC endpoint via <code>SecurityPolicy</code>, while the public card stays open.</li>
<li class="">Optionally, a <strong>gateway-served agent card</strong> so clients discover the gateway URL rather than the agent&#x27;s internal address.</li>
</ul>
<p>What you do <strong>not</strong> get yet: aggregation of several agents behind one card, rewriting of the backend&#x27;s own card, method-level authorization, or support for the gRPC and HTTP+JSON bindings. See <a href="#limitations" class="">Limitations</a>.</p>
<h2 class="anchor anchorTargetStickyNavbar_Vzrq" id="prerequisites">Prerequisites<a href="#prerequisites" class="hash-link" aria-label="Direct link to Prerequisites" title="Direct link to Prerequisites" translate="no">​</a></h2>
\<ul\>
<li class="">Agent Router installed following <a class="" href="/docs/getting-started/prerequisites">Prerequisites</a>. The Envoy Gateway values file used there already sets <code>extensionApis.enableEnvoyPatchPolicy: true</code>.</li>
<li class="">Envoy Gateway v1.8 or newer. The A2A filter exists since Envoy Proxy v1.38.0, which Envoy Gateway v1.8 is the first release to ship; see the <a href="https://gateway.envoyproxy.io/news/releases/matrix/" target="_blank" rel="noopener noreferrer" class="">compatibility matrix</a> for later pairings. On an older proxy image the patched listener is rejected by Envoy, which takes every route on that listener down, so check the image before you start.</li>
<li class="">An A2A agent speaking the JSON-RPC binding. The example below assumes it runs as <code>Service/research-agent</code> on port 8080 in namespace <code>default</code>.</li>
</ul>
<div class="theme-admonition theme-admonition-warning admonition_xJq3 alert alert--warning"><div class="admonitionHeading_Gvgb"><span class="admonitionIcon_Rf37"><svg viewBox="0 0 16 16"><path fill-rule="evenodd" d="M8.893 1.5c-.183-.31-.52-.5-.887-.5s-.703.19-.886.5L.138 13.499a.98.98 0 0 0 0 1.001c.193.31.53.501.886.501h13.964c.367 0 .704-.19.877-.5a1.03 1.03 0 0 0 .01-1.002L8.893 1.5zm.133 11.497H6.987v-2.003h2.039v2.003zm0-3.004H6.987V5.987h2.039v4.006z"></path></svg></span>warning</div><div class="admonitionContent_BuS1"><p><code>EnvoyPatchPolicy</code> lets anyone with permission to create it inject arbitrary proxy configuration. The A2A filter itself is marked alpha with an unknown security posture in Envoy: use it only where both clients and agents are trusted.</p></div></div>

<p>To try a newer Envoy Proxy before Envoy Gateway ships it, override the proxy image in the <code>EnvoyProxy</code> resource as described in <a href="https://gateway.envoyproxy.io/docs/tasks/operations/customize-envoyproxy/" target="_blank" rel="noopener noreferrer" class="">Customize EnvoyProxy</a>. Keep in mind that the A2A filter is alpha, so its config and behaviour can change between releases; re-read the release notes before bumping.</p>
<h2 class="anchor anchorTargetStickyNavbar_Vzrq" id="limitations">Limitations<a href="#limitations" class="hash-link" aria-label="Direct link to Limitations" title="Direct link to Limitations" translate="no">​</a></h2>
<p>These reflect the filter as it ships today and will shrink as Envoy and Agent Router evolve. Check <a href="#keeping-up-with-envoy" class="">Keeping up with Envoy</a> for what your proxy version supports.</p>
\<ul\>
<li class=""><strong>A2A 1.0 method names are only partly modelled.</strong> The filter validates every request and logs <code>method</code> and <code>id</code>, but <code>taskId</code> and <code>contextId</code> extraction currently keys on the A2A 0.3 names (<code>message/send</code>, <code>tasks/get</code>, ...).</li>
<li class=""><strong><code>parser_config</code> and <code>storage_mode</code> are accepted but not yet wired up.</strong> Leave them unset until a release note says otherwise.</li>
<li class=""><strong><code>max_request_body_size</code> applies in both modes.</strong> A JSON-RPC envelope that is not complete within the limit gets a 413 even in <code>PASS_THROUGH</code>.</li>
<li class=""><strong><code>REJECT</code> suits JSON-RPC-only listeners.</strong> Route the gRPC and HTTP+JSON bindings on a listener without the filter.</li>
<li class=""><strong>Agent cards are served as-is, one per hostname.</strong> URL rewriting, aggregation and <code>aigw run</code> support are part of the first-class A2A work in <a href="https://github.com/theagentrouter/agent-router/issues/2070" target="_blank" rel="noopener noreferrer" class="">issue #2070</a>.</li>
