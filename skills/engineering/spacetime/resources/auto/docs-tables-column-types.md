markdown">\<header\>\<h1\>Column Types</h1></header><p>Columns define the structure of your tables. SpacetimeDB supports primitive types, composite types for complex data, and special types for database-specific functionality.</p>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="representing-collections">Representing Collections<a href="#representing-collections" class="hash-link" aria-label="Direct link to Representing Collections" title="Direct link to Representing Collections" translate="no">​</a></h2>
<p>When modeling data that contains multiple items, you have two choices: store the collection as a column (using <code>Vec</code>, <code>List</code>, or <code>Array</code>) or store each item as a row in a separate table. This decision affects how you query, update, and subscribe to that data.</p>
<p><strong>Use a collection column when:</strong></p>
\<ul\>
<li class="">The items form an atomic unit that you always read and write together</li>
<li class="">Order is semantically important and frequently accessed by position</li>
<li class="">The collection is small and bounded (e.g., a fixed-size inventory)</li>
<li class="">The items are values without independent identity</li>
</ul>
<p><strong>Use a separate table when:</strong></p>
\<ul\>
<li class="">Items have independent identity and lifecycle</li>
<li class="">You need to query, filter, or index individual items</li>
<li class="">The collection can grow unbounded</li>
<li class="">Clients should receive updates for individual item changes, not the entire collection</li>
<li class="">You want to enforce referential integrity between items and other data</li>
</ul>
<p>Consider a game inventory with ordered pockets. A <code>Vec<Item></code> preserves pocket order naturally, but if you need to query "all items owned by player X" across multiple players, a separate <code>inventory_item</code> table with a <code>pocket_index</code> column allows that query efficiently. The right choice depends on your dominant access patterns.</p>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="binary-data-and-files">Binary Data and Files<a href="#binary-data-and-files" class="hash-link" aria-label="Direct link to Binary Data and Files" title="Direct link to Binary Data and Files" translate="no">​</a></h2>
<p>SpacetimeDB includes optimizations for storing binary data as <code>Vec\<u8\></code> (Rust), <code>List<byte></code> (C#), <code>t.array(t.u8())</code> (TypeScript), or <code>std::vector\<uint8_t\></code> (C++). You can store files, images, serialized data, or other binary blobs directly in table columns.</p>
<p>This approach works well when:</p>
\<ul\>
<li class="">The binary data is associated with a specific row (e.g., a user&#x27;s avatar image)</li>
<li class="">You want the data to participate in transactions and subscriptions</li>
<li class="">The data size is reasonable (up to several megabytes per row)</li>
</ul>
<p>For very large files or data that changes independently of other row fields, consider external storage with a reference stored in the table.</p>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="type-performance">Type Performance<a href="#type-performance" class="hash-link" aria-label="Direct link to Type Performance" title="Direct link to Type Performance" translate="no">​</a></h2>
<p>SpacetimeDB optimizes reading and writing by taking advantage of memory layout. Several factors affect performance:</p>
<p><strong>Prefer smaller types.</strong> Use the smallest integer type that fits your data range. A <code>u8</code> storing values 0-255 uses less memory and bandwidth than a <code>u64</code> storing the same values. This reduces storage, speeds up serialization, and improves cache efficiency.</p>
<p><strong>Prefer fixed-size types.</strong> Fixed-size types (<code>u32</code>, <code>f64</code>, fixed-size structs) allow SpacetimeDB to compute memory offsets directly. Variable-size types (<code>String</code>, <code>Vec\<T\></code>) require additional indirection. When performance matters, consider fixed-size alternatives:</p>
\<ul\>
<li class="">Use <code>[u8; 32]</code> instead of <code>Vec\<u8\></code> for fixed-length hashes or identifiers</li>
<li class="">Use an enum with a fixed set of variants instead of a <code>String</code> for categorical data</li>
</ul>
<p><strong>Consider column ordering.</strong> Types require alignment in memory. A <code>u64</code> aligns to 8-byte boundaries, while a <code>u8</code> aligns to 1-byte boundaries. When smaller types precede larger ones, the compiler may insert padding bytes to satisfy alignment requirements. Ordering columns from largest to smallest alignment can reduce padding and improve memory density.</p>
<p>For example, a struct with fields <code>(u8, u64, u8)</code> may require 24 bytes due to padding, while <code>(u64, u8, u8)</code> requires only 16 bytes. This optimization is not something to follow religiously, but it can help performance in memory-intensive scenarios.</p>
<p>These optimizations apply across all supported languages.</p>
