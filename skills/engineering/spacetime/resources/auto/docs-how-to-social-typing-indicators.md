class="admonitionContent_STxx"><p>You need a chat app. This guide builds on the one from the <a class="" href="/docs/tutorials/chat-app">chat app tutorial</a>: it uses its <code>user</code> and <code>message</code> tables, and its <code>send_message</code> reducer. If you don&#x27;t have a chat app yet, follow the tutorial for your language first.</p></div></div>
<p>In this guide, you&#x27;ll show who&#x27;s typing in the chat, such as "Alice is typing…". Typing signals only matter for a few seconds, so you&#x27;ll send them through an <a class="" href="/docs/tables/event-tables">event table</a>: its rows go to the clients, then the database deletes them.</p>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="how-it-works">How it works<a href="#how-it-works" class="hash-link" aria-label="Direct link to How it works" title="Direct link to How it works" translate="no">​</a></h2>
\<ul\>
<li class="">A public <code>typing_event</code> event table has one column: the <code>sender</code>.</li>
<li class="">A <code>start_typing</code> reducer inserts a row, with the caller as the sender. When the reducer&#x27;s transaction commits, SpacetimeDB sends the row to every subscribed client, then deletes it.</li>
<li class="">While the user types, the client calls <code>start_typing</code>, at most once every 2 seconds.</li>
<li class="">Each client keeps a list of who is typing. A user stays in it for 3 seconds after their last signal, or until they send a message. The client shows "Alice is typing…" from that list.</li>
</ul>
<p>You could store who&#x27;s typing in a regular table instead, but then you&#x27;d have to delete each row once the user stops typing. Typing signals don&#x27;t need to be stored: a client that connects later doesn&#x27;t need to know who was typing a second ago. An event table is always empty between transactions, so there&#x27;s nothing to clean up.</p>

<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="show-whos-typing">Show who&#x27;s typing<a href="#show-whos-typing" class="hash-link" aria-label="Direct link to Show who&#x27;s typing" title="Direct link to Show who&#x27;s typing" translate="no">​</a></h2>
<p>On the client, subscribe to <code>typing_event</code>, along with <code>user</code> and <code>message</code>. The client cache never keeps the rows of an event table, so you can&#x27;t read them back later: handle each signal in an <code>onInsert</code> callback, when it arrives.</p>
<p>Keep a list of who is typing, and when each of them stops showing as typing:</p>
\<ul\>
<li class="">When a signal arrives, set its sender to stop showing 3 seconds from now. Skip your own signals, so you don&#x27;t see yourself typing.</li>
<li class="">When a message arrives, remove its sender: they&#x27;re done typing.</li>
<li class="">A few times per second, remove the users whose 3 seconds are up.</li>
</ul>
<p>Each client uses its own clock for these deadlines, so it doesn&#x27;t matter if the clocks of the clients and the database disagree. The timeout is longer than the interval between signals, so a user who keeps typing doesn&#x27;t flicker on and off when a signal arrives a little late.</p>

<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="whats-next">What&#x27;s next?<a href="#whats-next" class="hash-link" aria-label="Direct link to What&#x27;s next?" title="Direct link to What&#x27;s next?" translate="no">​</a></h2>
<p>You now show who&#x27;s typing in the chat:</p>
\<ul\>
<li class="">A public event table carries the typing signals. Its rows go to the subscribed clients, and are never stored, so there&#x27;s nothing to clean up.</li>
<li class="">A reducer sets the sender of each signal itself.</li>
<li class="">Clients send at most one signal every 2 seconds, and show each user as typing for 3 seconds after their last one, or until they send a message.</li>
</ul>
<p>To adapt it to your app:</p>
\<ul\>
<li class=""><strong>Chat rooms.</strong> Add a <code>room_id</code> column to <code>typing_event</code>, and a <code>room_id</code> argument to <code>start_typing</code> that it checks the caller is in. Clients then show only the signals of the room that&#x27;s open. With many rooms, subscribe only to the open room&#x27;s signals, with a query that filters on <code>room_id</code>.</li>
<li class=""><strong>Private signals.</strong> Event tables can&#x27;t be used in views, so every client that subscribes to <code>typing_event</code> can receive every signal. That&#x27;s fine for a chat that everyone can read, but not for a private room or a DM. For those, store who&#x27;s typing in a private table, give each user the rows they may see through a <a class="" href="/docs/functions/views">view</a>, as in <a class="" href="/docs/how-to/social/chat-rooms-and-dms">Chat rooms and private DMs</a>, and delete old rows with a <a class="" href="/docs/tables/schedule-tables">scheduled reducer</a>.</li>
<li class=""><strong>Stop typing right away.</strong> To hide the indicator as soon as the user clears the message box, add a <code>typing</code> column to <code>typing_event</code>, and a <code>stop_typing</code> reducer that inserts a row with <code>typing</code> set to false. Clients remove the sender when they receive it.</li>
<li class=""><strong>Spam.</strong> A client can call <code>start_typing</code> much more often than every 2 seconds. To stop that, store when each user last signaled in a private table, and ignore signals that come too soon. The <a class="" href="/docs/how-to/social/unique-usernames">usernames guide</a> uses the same kind of cooldown for name requests.</li>
<li class=""><strong>Other short-lived signals.</strong> The same pattern works for anything clients only need to see as it happens: emoji reactions, "Alice joined the chat" notices, pings or sound effects. Give each kind of signal its own event table, with the columns it needs.</li>
</ul>
<p>To learn more about the features used here, see <a class="" href="/docs/tables/event-tables">Event Tables</a> and <a class="" href="/docs/functions/reducers">Reducers</a>.</p>
