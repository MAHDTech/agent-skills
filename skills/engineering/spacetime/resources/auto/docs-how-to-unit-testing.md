type="button" class="clean-btn tocCollapsibleButton_Dk1U">On this page</button></div><div class="theme-doc-markdown markdown">\<header\>\<h1\>Unit Test Modules</h1></header>
<p>A module&#x27;s reducers, procedures and views are ordinary functions, and most of what they do is read and write tables. Spacetime includes a test harness that runs those functions against an in-memory datastore built from your module&#x27;s schema, so you can unit test them without publishing a database or running a Spacetime host.</p>
<p>The datastore is the real one, not a mock or a simulator, so tables enforce their constraints and transactions roll back exactly as they would in production. Because it runs in-process and in-memory, a fresh test database takes about a millisecond to create. Each test can have its own, and tests are fast, isolated and deterministic.</p>
<p>The harness controls everything a function would otherwise get from the host: who the caller is, what time it is, the random number seed and, for procedures, the replies to outgoing HTTP requests.</p>
<p>The test utilities are available in the <code>spacetimedb</code> module libraries starting with version <strong>2.12.0</strong>. These are server-module tests, not client SDK tests. Keep integration tests against a running server for subscriptions, network connections, deployment, and durability behavior.</p>

Run the commands from your module directory, usually <code>spacetimedb/</code>.</p>

<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="choose-the-caller">Choose the caller<a href="#choose-the-caller" class="hash-link" aria-label="Direct link to Choose the caller" title="Direct link to Choose the caller" translate="no">​</a></h2>
<p>Every call into the module is made by someone, which decides <code>ctx.sender</code>. Each test call takes a <code>TestAuth</code> saying who the caller is, and there are two kinds of caller:</p>
\<ul\>
<li class=""><strong>The database itself.</strong> Use it for <a href="#test-scheduled-reducers" class="">scheduled reducers</a>, which the database calls on its own behalf. The sender is the module identity, there is no connection ID or JWT, and the reducer&#x27;s context reports the call as internal.</li>
<li class=""><strong>A client</strong>, built from a JSON claims payload, not a signed token, and a connection ID. Use it for reducers that clients call, and for the client connected and client disconnected lifecycle reducers. The sender is derived from the <code>iss</code> and <code>sub</code> claims, so the same issuer and subject always give the same identity. The reducer sees the claims as it would for a real connection, including any custom claims. This tests module logic that reads claims; it does not test production JWT signature verification.</li>
</ul>
<p>The <code>init</code> <a class="" href="/docs/functions/reducers/lifecycle">lifecycle reducer</a> is neither. On a published database its sender is the identity that owns the database, usually whoever published it, not the module identity. If your <code>init</code> ignores <code>ctx.sender</code>, either caller will do. If it reads the sender, for example to record an owner who alone may call admin reducers, call it as a client standing in for the publisher, and use that same client for the owner&#x27;s calls later in the test. Calling it as the database itself would record the module identity as the owner, and the test&#x27;s owner-only calls would then be refused.</p>
<p>The harness does not simulate clients connecting or automatically call your initialization or connection reducers. Invoke those functions explicitly inside a test transaction when they are part of your setup, as the chat templates do.</p>

<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="check-which-tokens-a-client-may-connect-with">Check which tokens a client may connect with<a href="#check-which-tokens-a-client-may-connect-with" class="hash-link" aria-label="Direct link to Check which tokens a client may connect with" title="Direct link to Check which tokens a client may connect with" translate="no">​</a></h3>
<p>A client connected reducer runs as the connecting client, so a test can check which tokens it accepts. This connect reducer accepts only tokens from your own auth provider that were issued for your application, and returning an error from it is what rejects the connection. It checks both claims: the issuer says who signed the token, and the audience says which application it was meant for. Checking only one would let a token from another provider, or one issued for another application, through. See <a class="" href="/docs/core-concepts/authentication/usage#example-restricting-auth-providers">Restricting auth providers</a> for the full guidance.</p>

<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="set-up-and-inspect-tables">Set up and inspect tables<a href="#set-up-and-inspect-tables" class="hash-link" aria-label="Direct link to Set up and inspect tables" title="Direct link to Set up and inspect tables" translate="no">​</a></h2>
<p>The harness reads and writes the tables directly through <code>test.db</code>, outside any reducer, with the same accessors as a reducer&#x27;s <code>ctx.db</code>. Use this to put the database into the state a test needs, rather than reaching that state through a series of reducer calls, and to check the result afterwards. Rows written this way obey the table&#x27;s constraints, so inserting a duplicate primary key fails just as it would in a reducer.</p>
<p>Create a new harness or context per test. In Rust, <code>TestContext::clone()</code> shares the existing database rather than creating an independent one.</p>
<p>The order of rows returned by <code>iter()</code> is not guaranteed. Sort them before comparing against a list, as the <a href="#test-scheduled-reducers" class="">scheduled reducer example</a> does.</p>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="control-time">Control time<a href="#control-time" class="hash-link" aria-label="Direct link to Control time" title="Direct link to Control time" translate="no">​</a></h2>

<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="test-procedures-and-http">Test procedures and HTTP<a href="#test-procedures-and-http" class="hash-link" aria-label="Direct link to Test procedures and HTTP" title="Direct link to Test procedures and HTTP" translate="no">​</a></h2>
<p>A <a class="" href="/docs/functions/procedures">procedure</a> runs outside a transaction and opens its own, so the harness gives it a procedure context rather than wrapping it in a transaction. Create a procedure context for a caller and call the procedure with it.</p>
<div class="theme-tabs-container tabs-container tabList_duiv"><ul role="tablist" aria-orientation="horizontal" class="tabs"><li role="tab" tabindex="0" aria-selected="true" class="tabs__item tabItem_a1H9 tabs__item--active">TypeScript</li><li role="tab" tabindex="-1" aria-selected="false" class="tabs__item tabItem_a1H9">Rust</li></ul><div class="margin-top--md"><div role="tabpanel" class="tabItem_w6aI"><p>Create a procedure context with <code>test.procedureContext(auth)</code>. Inside the procedure, <code>ctx.withTx(...)</code> does the database work.</p></div><div role="tabpanel" class="tabItem_w6aI" hidden=""><p>Procedure APIs require the <code>unstable</code> feature on the dev-dependency: <code>features = ["test-utils", "unstable"]</code>. Create a procedure context with <code>test.procedure_context(auth)</code>. Use <code>ctx.try_with_tx(...)</code> for database work; <code>ctx.with_tx(...)</code> currently panics in tests (<a href="https://github.com/clockworklabs/SpacetimeDB/pull/6296" target="_blank" rel="noopener noreferrer" class="">#6296</a>).</p></div></div></div>

<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="test-what-clients-will-see">Test what clients will see<a href="#test-what-clients-will-see" class="hash-link" aria-label="Direct link to Test what clients will see" title="Direct link to Test what clients will see" translate="no">​</a></h2>
<p>A test can&#x27;t subscribe, but it can check the <a class="" href="/docs/functions/views">views</a> and queries that clients subscribe to. Call a view with a context for a chosen caller, and check what it returns. This makes per-user views testable: call the same view as two different clients and check that each sees only their own rows.</p>
<p>The harness builds a view context for a chosen caller, or an anonymous one for anonymous views. A view that returns rows gives them back directly. A view that returns a typed query gives back the query, which the harness runs against the committed tables.</p>
<p>Queries run in a test always run as the database owner, which bypasses <a class="" href="/docs/how-to/rls">row-level security</a> and can read private tables. A query&#x27;s results are therefore the rows it matches, not necessarily the rows a particular client would receive.</p>

<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="limitations">Limitations<a href="#limitations" class="hash-link" aria-label="Direct link to Limitations" title="Direct link to Limitations" translate="no">​</a></h2>
\<ul\>
<li class=""><strong>Scheduled reducers don&#x27;t run automatically.</strong> Rows in schedule tables are stored, but no timer fires. Call scheduled reducers directly, as shown <a href="#test-scheduled-reducers" class="">above</a>.</li>
<li class=""><strong>No subscriptions or clients.</strong> The harness doesn&#x27;t deliver rows to subscribers or run client callbacks. Test the views and queries clients subscribe to instead, as shown <a href="#test-what-clients-will-see" class="">above</a>.</li>
<li class=""><strong>No row-level security.</strong> Queries run as the database owner, so they ignore row-level security rules and can read private tables.</li>
<li class=""><strong>Views can&#x27;t be queried by name.</strong> Call the view&#x27;s function instead.</li>
<li class=""><strong>No lifecycle simulation.</strong> Connecting, disconnecting and publishing don&#x27;t call lifecycle reducers. Call them explicitly.</li>
</ul>
<div class="theme-tabs-container tabs-container tabList_duiv"><ul role="tablist" aria-orientation="horizontal" class="tabs"><li role="tab" tabindex="0" aria-selected="true" class="tabs__item tabItem_a1H9 tabs__item--active">TypeScript</li><li role="tab" tabindex="-1" aria-selected="false" class="tabs__item tabItem_a1H9">Rust</li></ul><div class="margin-top--md"><div role="tabpanel" class="tabItem_w6aI">\<ul\>
<li class=""><strong>Host functions outside the datastore.</strong> Module code that calls a host function the harness doesn&#x27;t provide, such as <code>volatile_nonatomic_schedule_immediate</code>, throws <code>Unsupported SpacetimeDB host syscall in module unit test</code>.</li>
</ul><h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="known-issues">Known issues<a href="#known-issues" class="hash-link" aria-label="Direct link to Known issues" title="Direct link to Known issues" translate="no">​</a></h3>\<ul\>
<li class=""><strong>Range scans on indexes</strong> (<a href="https://github.com/clockworklabs/SpacetimeDB/issues/6299" target="_blank" rel="noopener noreferrer" class="">#6299</a>). The test utilities bundle their own copy of the SDK runtime, so a <code>Range</code> imported from <code>spacetimedb/server</code> in module code isn&#x27;t recognized as a range by the harness. An index <code>filter</code> or <code>delete</code> with a <code>Range</code> is treated as a point lookup instead: on a number column it silently matches no rows, and on a bigint-backed column, such as a timestamp, it throws <code>Cannot convert undefined to a BigInt</code>. The silent case can make a test of range deletion pass when nothing was deleted. A published database is unaffected.</li>
<li class=""><strong>Event table rows written outside a reducer transaction persist.</strong> <a class="" href="/docs/tables/event-tables">Event table</a> rows inserted inside <code>withReducerTx</code> are deleted when the transaction commits, as on a published database. Rows inserted directly through the harness&#x27;s <code>test.db</code>, or by a procedure&#x27;s <code>withTx</code>, stay in the table.</li>
</ul></div><div role="tabpanel" class="tabItem_w6aI" hidden=""><h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="known-issues-1">Known issues<a href="#known-issues-1" class="hash-link" aria-label="Direct link to Known issues" title="Direct link to Known issues" translate="no">​</a></h3>\<ul\>
<li class=""><strong><code>ProcedureContext::with_tx</code> panics</strong> (<a href="https://github.com/clockworklabs/SpacetimeDB/pull/6296" target="_blank" rel="noopener noreferrer" class="">#6296</a>). In a test, <code>with_tx</code> makes host calls instead of using the test datastore, and panics with <code>holding &mut HandlerContext, so should not be in a tx already</code>. Use <code>try_with_tx</code> in procedures you want to test until the fix is released.</li>
<li class=""><strong>Projects from the <code>chat-console-rs</code> template have an invalid dev-dependency</strong> (<a href="https://github.com/clockworklabs/SpacetimeDB/issues/6298" target="_blank" rel="noopener noreferrer" class="">#6298</a>). <code>spacetime init</code> writes the template&#x27;s <code>spacetimedb</code> dev-dependency with a <code>path</code> into the SpacetimeDB repository. Replace it with a version that matches the normal dependency, as shown in <a href="#enable-the-test-utilities" class="">Enable the test utilities</a>.</li>
</ul></div></div></div>
