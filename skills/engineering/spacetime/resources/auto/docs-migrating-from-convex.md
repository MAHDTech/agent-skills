markdown">\<header\>\<h1\>Migrating from Convex</h1></header>
<p>This guide is for teams moving an application backend from Convex to a
SpacetimeDB module. Convex and SpacetimeDB both combine database state, server
logic, generated clients, and live updates, but the programming models are not
identical. The most important shift is:</p>
\<ul\>
<li class="">In Convex, clients call <strong>queries</strong> to read data and <strong>mutations</strong> to write
data.</li>
<li class="">In SpacetimeDB, clients <strong>subscribe</strong> to tables or views to read live data and
call <strong>reducers</strong> to change state.</li>
</ul>
<p>Reducers do not return application data. They commit database changes, and
clients observe the resulting rows through subscriptions, views, and event
tables. Use procedures only when you need side effects such as outbound HTTP.</p>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="terminology-map">Terminology Map<a href="#terminology-map" class="hash-link" aria-label="Direct link to Terminology Map" title="Direct link to Terminology Map" translate="no">​</a></h2>
<table><thead><tr><th>Convex term</th><th>SpacetimeDB term</th><th>Migration notes</th></tr></thead>\<tbody\><tr><td>Project</td><td>Project plus module source tree</td><td>A SpacetimeDB project contains module code, generated bindings, and client code.</td></tr><tr><td>Deployment</td><td>Database</td><td>A published SpacetimeDB module creates or updates a database on Maincloud or a self-hosted host.</td></tr><tr><td>Backend</td><td>Database plus module</td><td>Your module contains tables and callable functions that run inside the database.</td></tr><tr><td><code>convex/</code> directory</td><td><code>spacetimedb</code> directory</td><td>TypeScript templates usually put module code in <code>spacetimedb/src/index.ts</code>. Rust, C#, and C++ use their normal project layouts.</td></tr><tr><td><code>schema.ts</code></td><td>Table definitions in module code</td><td>SpacetimeDB schema is declared in the module language using <a class="" href="/docs/tables">tables</a>.</td></tr><tr><td><code>defineSchema</code></td><td><code>schema(...)</code> or language-specific module schema</td><td>In TypeScript, pass tables created with <code>table()</code> to <code>schema({ tableName })</code>.</td></tr><tr><td><code>defineTable</code></td><td><code>table()</code></td><td>Tables store rows and define columns, constraints, indexes, visibility, and optional scheduling.</td></tr><tr><td>Table</td><td>Table</td><td>Both systems organize persistent data into named tables.</td></tr><tr><td>Document</td><td>Row</td><td>SpacetimeDB tables are relational rows, not JSON-like documents.</td></tr><tr><td>Document field</td><td>Column</td><td>Columns have static SpacetimeDB types.</td></tr><tr><td>Document ID / <code>Id<"table"></code></td><td>Primary key, unique key, or <code>Identity</code></td><td>Choose the key based on access pattern. Use <code>autoInc()</code> for generated numeric IDs, <code>Identity</code> for users, and unique constraints for alternate lookup keys.</td></tr><tr><td><code>_id</code></td><td>Primary key column</td><td>Name it explicitly, commonly <code>id</code>. SpacetimeDB does not require a universal <code>_id</code> column.</td></tr><tr><td><code>_creationTime</code></td><td>Explicit timestamp column</td><td>Add a <code>Timestamp</code> column and set it from <code>ctx.timestamp</code> if you need creation time.</td></tr><tr><td>Validators (<code>v.string()</code>, <code>v.id()</code>, etc.)</td><td>Column and argument types (<code>t.string()</code>, <code>t.u64()</code>, <code>t.identity()</code>, etc.)</td><td>SpacetimeDB validates values through the module schema and generated bindings.</td></tr><tr><td>Query</td><td>View function, subscription, or SQL query</td><td>Use a <a class="" href="/docs/functions/views">view</a> for server-side computed read results. Use a <a class="" href="/docs/clients/subscriptions">subscription</a> when the client needs live rows in its cache.</td></tr><tr><td>Mutation</td><td>Reducer</td><td>Use a <a class="" href="/docs/functions/reducers">reducer</a> for every normal state-changing operation. Reducers are transactional and deterministic.</td></tr><tr><td>Action</td><td>Procedure</td><td>Use a <a class="" href="/docs/functions/procedures">procedure</a> when the function needs side effects, especially outbound HTTP. If it only updates database state, migrate it to a reducer.</td></tr><tr><td>HTTP Action</td><td>HTTP handler</td><td>Use an <a class="" href="/docs/functions/http-handlers">HTTP handler</a> for inbound HTTP routes such as webhooks or public HTTP APIs. Use a procedure for callable side-effecting functions that are not HTTP endpoints.</td></tr><tr><td>Internal query / mutation / action</td><td>Private reducer, private procedure, helper function, or private table</td><td>Keep helper logic unexported when it should not be callable by clients. <h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="components-and-submodules">Components and Submodules<a href="#components-and-submodules" class="hash-link" aria-label="Direct link to Components and Submodules" title="Direct link to Components and Submodules" translate="no">​</a></h2>
<p>Convex <a href="https://www.convex.dev/components" target="_blank" rel="noopener noreferrer" class="">components</a> package reusable backend code and data. The SpacetimeDB equivalent is a <a class="" href="/docs/submodules">submodule</a>: a module you install from npm and include in your own module&#x27;s database. Submodules are TypeScript-only for now.</p>
<table><thead><tr><th>Convex component</th><th>SpacetimeDB submodule</th><th>Notes</th></tr></thead>\<tbody\><tr><td><code>@convex-dev/crons</code></td><td><code>@spacetimedb/cron</code></td><td>Calendar and interval schedules stored in your database, with time zones.</td></tr><tr><td><code>@convex-dev/rate-limiter</code></td><td><code>@spacetimedb/rate-limit</code></td><td>Fixed-window rate limiting.</td></tr><tr><td><code>@convex-dev/action-retrier</code></td><td><code>@spacetimedb/retry</code></td><td>Typed retries with exponential backoff and attempt history.</td></tr><tr><td><code>@convex-dev/resend</code></td><td><code>@spacetimedb/resend</code></td><td>Resend email delivery, webhook verification, and event storage.</td></tr><tr><td>None</td><td><code>@spacetimedb/crypto</code></td><td>Deterministic hashing, encoding, and webhook-signature helpers.</td></tr></tbody></table>
<p>Install a submodule from npm, for example <code>npm install @spacetimedb/cron spacetimedb</code>, and follow its README. If a component you use has no submodule yet, keep that logic in your own module, or package it as a submodule yourself.</p>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="migration-strategy">Migration Strategy<a href="#migration-strategy" class="hash-link" aria-label="Direct link to Migration Strategy" title="Direct link to Migration Strategy" translate="no">​</a></h2>
<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="1-inventory-your-convex-backend">1. Inventory your Convex backend<a href="#1-inventory-your-convex-backend" class="hash-link" aria-label="Direct link to 1. Inventory your Convex backend" title="Direct link to 1. Inventory your Convex backend" translate="no">​</a></h3>
<p>Start by listing every table and function in the Convex app:</p>
\<ul\>
<li class="">Tables in <code>convex/schema.ts</code>.</li>
<li class="">Queries used by UI components.</li>
<li class="">Mutations called from user actions.</li>
<li class="">Actions used for third-party APIs, emails, payments, search, AI, or other
side effects.</li>
<li class="">HTTP actions used for webhooks or public endpoints.</li>
<li class="">Scheduled functions and cron jobs.</li>
<li class="">Auth assumptions, especially user ID fields and provider-specific claims.</li>
<li class="">File storage usage.</li>
<li class="">Components and shared backend packages.</li>
</ul>
<p>Then classify each function by what it really does:</p>
\<ul\>
<li class=""><strong>Pure read</strong>: migrate to a view, a subscription, or a client-side read from
subscribed rows.</li>
<li class=""><strong>Database write</strong>: migrate to a reducer.</li>
<li class=""><strong>Side effect</strong>: migrate to a procedure, usually with a small transactional
reducer or <code>withTx</code> block around database changes.</li>
<li class=""><strong>Inbound HTTP</strong>: migrate to an HTTP handler.</li>
<li class=""><strong>Scheduled work</strong>: migrate to a schedule table that triggers a reducer or
procedure.</li>
</ul>
<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="2-redesign-tables-as-relational-rows">2. <h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="5-split-actions-into-reducers-and-procedures">5. Split actions into reducers and procedures<a href="#5-split-actions-into-reducers-and-procedures" class="hash-link" aria-label="Direct link to 5. Split actions into reducers and procedures" title="Direct link to 5. Split actions into reducers and procedures" translate="no">​</a></h3>
<p>Convex actions can call third-party services and can call queries or mutations.
In SpacetimeDB, keep deterministic database changes in reducers and move
side-effecting work to procedures.</p>
<p>Use this pattern for workflows such as payment processing:</p>
\<ol\>
<li class="">A reducer records the requested operation and validates the caller.</li>
<li class="">A procedure performs the external API call.</li>
<li class="">The procedure commits the resulting database changes with <code>withTx</code>, or calls
a reducer if the operation can be expressed as a normal state transition.</li>
</ol>
<p>Avoid doing network work in reducers. Reducers must be deterministic and
transactional.</p>
<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="6-replace-http-actions-with-http-handlers">6. Replace HTTP actions with HTTP handlers<a href="#6-replace-http-actions-with-http-handlers" class="hash-link" aria-label="Direct link to 6. Replace HTTP actions with HTTP handlers" title="Direct link to 6. Replace HTTP actions with HTTP handlers" translate="no">​</a></h3>
<p>Convex HTTP actions become SpacetimeDB HTTP handlers. Use them for webhooks,
OAuth callbacks, upload callbacks, and public HTTP APIs.</p>
<p>Use procedures instead when the caller is a SpacetimeDB client and the function
needs side effects but does not need an HTTP route.</p>

<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="8-migrate-scheduled-work">8. Migrate scheduled work<a href="#8-migrate-scheduled-work" class="hash-link" aria-label="Direct link to 8. Migrate scheduled work" title="Direct link to 8. Migrate scheduled work" translate="no">​</a></h3>
<p>Convex scheduled functions and cron jobs map to schedule tables. A schedule
table stores rows that cause a reducer or procedure to run at a specific time or
on an interval.</p>
<p>Use scheduled reducers for deterministic database maintenance. Use scheduled
procedures for jobs that need external I/O, such as sending email or calling a
third-party API.</p>
<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="9-migrate-files">9. Migrate files<a href="#9-migrate-files" class="hash-link" aria-label="Direct link to 9. Migrate files" title="Direct link to 9. Migrate files" translate="no">​</a></h3>
<p>Convex File Storage maps to one of two SpacetimeDB patterns:</p>
\<ul\>
<li class="">Store small binary data directly in table columns when it should be
transactional and live-updated with the row.</li>
<li class="">Store large files in object storage and keep metadata, ownership, and URLs in
SpacetimeDB tables.</li>
</ul>
<p>For browser uploads, a common pattern is:</p>
\<ol\>
<li class="">Client uploads the file to object storage using your existing upload flow.</li>
<li class="">Client calls a reducer to register metadata and ownership.</li>
<li class="">Other clients receive the metadata through subscriptions.</li>
</ol>
<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="10-migrate-components-and-shared-backend-code">10. Migrate components and shared backend code<a href="#10-migrate-components-and-shared-backend-code" class="hash-link" aria-label="Direct link to 10. Migrate components and shared backend code" title="Direct link to 10. Migrate components and shared backend code" translate="no">​</a></h3>
<p>Convex Components package code and data behind explicit interfaces. In
SpacetimeDB, model that boundary explicitly:</p>
\<ul\>
<li class="">Use submodules where they are available for reusable isolated systems.</li>
<li class="">Use separate modules/databases when you need operational isolation.</li>
<li class="">Keep reusable pure logic in normal language modules or packages.</li>
<li class="">Keep integration boundaries explicit with procedures, HTTP handlers, and
narrow table schemas.</li>
</ul>
<p>Do not give shared code direct access to unrelated tables just because it lives
in the same module. Preserve the interface boundary that made the Convex
component safe to reuse.</p>

<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="common-pitfalls">Common Pitfalls<a href="#common-pitfalls" class="hash-link" aria-label="Direct link to Common Pitfalls" title="Direct link to Common Pitfalls" translate="no">​</a></h2>
<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="expecting-reducers-to-return-data">Expecting reducers to return data<a href="#expecting-reducers-to-return-data" class="hash-link" aria-label="Direct link to Expecting reducers to return data" title="Direct link to Expecting reducers to return data" translate="no">​</a></h3>
<p>Reducers are for transactional state changes. If a Convex mutation returned data
that the UI needs, model that data as rows and subscribe to it. Use event tables
for transient messages and procedures for explicit request/response workflows
that require a return value.</p>
<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="porting-documents-without-normalization">Porting documents without normalization<a href="#porting-documents-without-normalization" class="hash-link" aria-label="Direct link to Porting documents without normalization" title="Direct link to Porting documents without normalization" translate="no">​</a></h3>
<p>A direct document-to-row conversion can create large rows that update too often
and produce unnecessary subscription traffic. Split tables by access pattern and
update frequency.</p>
<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="passing-user-ids-from-the-client">Passing user IDs from the client<a href="#passing-user-ids-from-the-client" class="hash-link" aria-label="Direct link to Passing user IDs from the client" title="Direct link to Passing user IDs from the client" translate="no">​</a></h3>
<p>Do not trust a user ID argument from the client for authorization. Use the
caller identity from the context and look up the user&#x27;s row from that identity.</p>
<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="using-procedures-for-normal-writes">Using procedures for normal writes<a href="#using-procedures-for-normal-writes" class="hash-link" aria-label="Direct link to Using procedures for normal writes" title="Direct link to Using procedures for normal writes" translate="no">​</a></h3>
<p>Procedures are powerful, but reducers are the default write path. Use reducers
unless you need procedure-only capabilities such as outbound HTTP.</p>
<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="forgetting-indexes">Forgetting indexes<a href="#forgetting-indexes" class="hash-link" aria-label="Direct link to Forgetting indexes" title="Direct link to Forgetting indexes" translate="no">​</a></h3>
<p>Convex query code often makes index usage visible with <code>withIndex(...)</code>.
SpacetimeDB needs the same design step: define indexes for the lookups and
subscriptions your app depends on.</p>
