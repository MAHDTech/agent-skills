class="admonitionContent_STxx"><p>You need a module and a client connected to it. If you don&#x27;t have them yet, follow the <a class="" href="/docs/">quickstart</a> for your language first. This guide uses a minimal <code>player</code> table with a name, and doesn&#x27;t cover how players get their row. To let players pick a unique name and block offensive ones, see <a class="" href="/docs/how-to/social/unique-usernames">Keep usernames unique and block offensive ones</a>: the code here works the same with its <code>player</code> table.</p></div></div>
<p>In this guide, you&#x27;ll let players follow each other, and show each player, live, who they follow and who follows them. Players who follow each other are mutual follows. Nobody else can see a player&#x27;s lists. You&#x27;ll store follows in a private table, and use <a class="" href="/docs/functions/views">views</a> built with the query builder to give each player their own lists.</p>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="how-it-works">How it works<a href="#how-it-works" class="hash-link" aria-label="Direct link to How it works" title="Direct link to How it works" translate="no">​</a></h2>
\<ul\>
<li class="">A public <code>player</code> table holds each player&#x27;s name. How a player gets their row is up to the rest of your module.</li>
<li class="">A private <code>follow</code> table has one row for each follow: <code>follower</code> follows <code>followed</code>. Both columns have an <a class="" href="/docs/tables/indexes">index</a>.</li>
<li class=""><code>follow_player</code> and <code>unfollow_player</code> reducers add and remove the caller&#x27;s follows. A <code>remove_follower</code> reducer lets players remove someone who follows them.</li>
<li class="">Two views, <code>my_following</code> and <code>my_followers</code>, return the <code>player</code> rows of the players the caller follows, and of the players who follow the caller.</li>
<li class="">Clients subscribe to both views. A player who is in both lists is a mutual follow.</li>
</ul>
<p>The <code>follow</code> table is private, so clients can&#x27;t read who follows whom. They only see the rows the views return, and each view only returns the caller&#x27;s own lists.</p>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="define-the-tables">Define the tables<a href="#define-the-tables" class="hash-link" aria-label="Direct link to Define the tables" title="Direct link to Define the tables" translate="no">​</a></h2>

<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="follow-and-unfollow-players">Follow and unfollow players<a href="#follow-and-unfollow-players" class="hash-link" aria-label="Direct link to Follow and unfollow players" title="Direct link to Follow and unfollow players" translate="no">​</a></h2>
<p>Add a <code>find_follow</code> function that returns the row recording that one player follows another, if there is one. It reads the follower&#x27;s follows through the <code>follower</code> index, and looks for the followed player among them.</p>
<p>Then add three reducers:</p>
\<ul\>
<li class=""><code>follow_player</code> makes the caller follow <code>target</code>. It rejects players who don&#x27;t have a <code>player</code> row yet, following yourself, and following a player who doesn&#x27;t exist. Following someone twice changes nothing, so a client that sends the request twice doesn&#x27;t get an error. It also limits each player to 1,000 follows, so that no one can follow every player in your game, and so that <code>find_follow</code> never reads more than 1,000 rows.</li>
<li class=""><code>unfollow_player</code> makes the caller stop following <code>target</code>.</li>
<li class=""><code>remove_follower</code> makes <code>follower</code> stop following the caller.</li>
</ul>

<p>These views return a query instead of rows, so SpacetimeDB evaluates them with its query engine. When a follow changes, it works out which rows of each view changed, instead of running the view again. Each view depends on who asks, so SpacetimeDB keeps one per subscribed player, but each one only covers that player&#x27;s follows.</p>
<p>The views return <code>player</code> rows, so they keep the <code>player</code> table&#x27;s primary key. When a player renames, clients receive the change as an update to the existing row.</p>

<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="use-it-as-a-friends-list">Use it as a friends list<a href="#use-it-as-a-friends-list" class="hash-link" aria-label="Direct link to Use it as a friends list" title="Direct link to Use it as a friends list" translate="no">​</a></h2>
<p>Follows are one-way, like on most social networks. To build friends that both players must agree on, like in most games, use the same table and reducers, and treat a follow that hasn&#x27;t been returned yet as a friend request:</p>
<table><thead><tr><th>In a friends list</th><th>With follows</th></tr></thead>\<tbody\><tr><td>Send a friend request</td><td><code>follow_player</code></td></tr><tr><td>Incoming requests</td><td>Players in <code>my_followers</code> but not in <code>my_following</code></td></tr><tr><td>Outgoing requests</td><td>Players in <code>my_following</code> but not in <code>my_followers</code></td></tr><tr><td>Accept a request</td><td><code>follow_player</code>, to follow them back</td></tr><tr><td>Decline a request</td><td><code>remove_follower</code></td></tr><tr><td>Friends</td><td>Mutual follows</td></tr><tr><td>Remove a friend</td><td><code>unfollow_player</code> and <code>remove_follower</code></td></tr></tbody></table>
<p>To remove a friend in a single transaction, add a reducer that deletes both rows.</p>
<p>After a decline, nothing stops the other player from sending the request again, as often as they like. To prevent that, add a block list: a private table of blocked players that <code>follow_player</code> checks before it adds a follow.</p>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="whats-next">What&#x27;s next?<a href="#whats-next" class="hash-link" aria-label="Direct link to What&#x27;s next?" title="Direct link to What&#x27;s next?" translate="no">​</a></h2>
<p>You now have follow lists that stay live on every client:</p>
\<ul\>
<li class="">A private <code>follow</code> table records who follows whom, with an index on each side.</li>
<li class="">Reducers add and remove follows, and limit how many players each player can follow.</li>
<li class="">Two views built with the query builder show each player their own lists, and update incrementally.</li>
<li class="">Clients find mutual follows by comparing the two lists, which also gives you a friends list with requests.</li>
</ul>
<p>From here, you could add a block list, as described above, or show which of a player&#x27;s follows are online.</p>
