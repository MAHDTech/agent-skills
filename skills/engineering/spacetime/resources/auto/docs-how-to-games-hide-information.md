<p>In this guide, you&#x27;ll build the hidden information of a card game: each player sees their own hand, but only how many cards the other players hold, and nobody sees the order of the deck. You&#x27;ll keep every table private, and give each player <a class="" href="/docs/functions/views">views</a> that return only what they&#x27;re allowed to see.</p>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="keep-tables-private">Keep tables private<a href="#keep-tables-private" class="hash-link" aria-label="Direct link to Keep tables private" title="Direct link to Keep tables private" translate="no">​</a></h2>
<p>Any client can subscribe to any row of a public table, whatever your game shows on screen. Hiding something in your client&#x27;s UI doesn&#x27;t hide it: a modified client can read the whole table, including other players&#x27; cards.</p>
<p>Private tables are the opposite. Clients can&#x27;t subscribe to them or query them, and they don&#x27;t even appear in the client bindings. Only your module&#x27;s code, and you as the database owner, can read them. Tables are private unless you mark them public.</p>
<p>To give clients the data they need, add views. A view runs on the server for the player who subscribes to it, and returns only the rows and columns that player may see. A modified client can&#x27;t get anything more out of it.</p>

Only make a table public if every row and every column is meant for every player, and will stay that way: it&#x27;s easy to add a secret column to a public table later and forget that everyone can read it.</p></div></div>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="how-it-works">How it works<a href="#how-it-works" class="hash-link" aria-label="Direct link to How it works" title="Direct link to How it works" translate="no">​</a></h2>
\<ul\>
<li class="">Four private tables hold each player&#x27;s game, the deck, each player&#x27;s hand and the cards played.</li>
<li class="">A <code>start_game</code> function shuffles the deck and deals a hand to each player.</li>
<li class="">The <code>draw_card</code> and <code>play_card</code> reducers move cards from the deck to a hand, and from a hand to the table.</li>
<li class="">Three views give each player their own hand, how many cards each player in their game holds, and the cards played in their game.</li>
</ul>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="define-the-tables">Define the tables<a href="#define-the-tables" class="hash-link" aria-label="Direct link to Define the tables" title="Direct link to Define the tables" translate="no">​</a></h2>
<p>Add four tables, all private:</p>
\<ul\>
<li class=""><code>game_player</code> records which game each player is in.</li>
<li class=""><code>deck_card</code> holds the cards left in each game&#x27;s deck. The card with the lowest <code>id</code> is the top of the deck.</li>
<li class=""><code>hand_card</code> holds the cards in each player&#x27;s hand, with an index on the player holding them.</li>
<li class=""><code>played_card</code> holds the cards played face up in each game.</li>
</ul>
<p>A card is a number from 0 to 51, which clients turn into a rank and a suit.</p>

<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="deal-the-cards">Deal the cards<a href="#deal-the-cards" class="hash-link" aria-label="Direct link to Deal the cards" title="Direct link to Deal the cards" translate="no">​</a></h2>
<p>Add a <code>start_game</code> function that shuffles a 52-card deck, deals 5 cards to each player, and stores the rest of the deck in shuffled order.</p>
<p><code>start_game</code> isn&#x27;t a reducer, so clients can&#x27;t call it. Call it from your matchmaking when a match is created, with the match&#x27;s id and its players. See the <a class="" href="/docs/how-to/games/matchmaking-queue">matchmaking queue</a> guide.</p>
<p>When a game ends, delete its players&#x27; <code>game_player</code> and <code>hand_card</code> rows, and its <code>deck_card</code> and <code>played_card</code> rows. Otherwise its players can&#x27;t start another game: <code>start_game</code> would fail to add them to <code>game_player</code> again.</p>

<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="draw-and-play-cards">Draw and play cards<a href="#draw-and-play-cards" class="hash-link" aria-label="Direct link to Draw and play cards" title="Direct link to Draw and play cards" translate="no">​</a></h2>
<p>Add two reducers:</p>
\<ul\>
<li class=""><code>draw_card</code> moves the top card of the caller&#x27;s deck into their hand.</li>
<li class=""><code>play_card</code> moves a card from the caller&#x27;s hand to the cards played in their game. It rejects cards the caller doesn&#x27;t hold.</li>
</ul>
<p>Errors are sent back to the player who called the reducer, so they must not reveal anything about other players. <code>play_card</code> returns the same error whether the card doesn&#x27;t exist or is in another player&#x27;s hand.</p>
<p>Other players don&#x27;t see which reducers you call or their arguments. They only see the changes to the views they subscribe to.</p>

<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="give-each-player-their-own-views">Give each player their own views<a href="#give-each-player-their-own-views" class="hash-link" aria-label="Direct link to Give each player their own views" title="Direct link to Give each player their own views" translate="no">​</a></h2>
<p>Add three public views. Each one depends on who is asking, so SpacetimeDB computes it separately for each subscribed player:</p>
\<ul\>
<li class=""><code>my_hand</code> returns the caller&#x27;s cards. It&#x27;s a single filter, so it returns a query instead of rows: SpacetimeDB then keeps it up to date the same way as a subscription query, without re-running the view.</li>
<li class=""><code>played_cards</code> returns the cards played in the caller&#x27;s game. It&#x27;s also a query: it finds the caller&#x27;s <code>game_player</code> row, then the played cards with the same game id.</li>
<li class=""><code>my_table</code> returns every player in the caller&#x27;s game with the number of cards they hold. It returns a <code>Seat</code> type instead of <code>hand_card</code> rows, so other players&#x27; cards never leave the server: a view decides which columns players see, not just which rows.</li>
</ul>
<p>Because SpacetimeDB computes these views for each player, keep them small: each one reads a few rows through indexes. See <a class="" href="/docs/functions/views#performance-why-anonymousviewcontext-matters">Views</a> for how they&#x27;re evaluated.</p>

<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="whats-next">What&#x27;s next?<a href="#whats-next" class="hash-link" aria-label="Direct link to What&#x27;s next?" title="Direct link to What&#x27;s next?" translate="no">​</a></h2>
<p>Each player now sees exactly what they&#x27;re allowed to, and a modified client can&#x27;t see more:</p>
\<ul\>
<li class="">All four tables are private, so clients can&#x27;t read the deck or anyone&#x27;s hand directly.</li>
<li class=""><code>my_hand</code> and <code>played_cards</code> return only the caller&#x27;s cards and the cards played in their game.</li>
<li class=""><code>my_table</code> tells each player how many cards the others hold, without their cards.</li>
<li class="">Errors from <code>play_card</code> don&#x27;t reveal other players&#x27; cards.</li>
</ul>
<p>To adapt it to your game:</p>
\<ul\>
<li class=""><strong>Show how many cards are left in the deck.</strong> Add it to a view the same way as the hand sizes: count the <code>deck_card</code> rows of the caller&#x27;s game.</li>
<li class=""><strong>Reveal hands at the end of a round.</strong> A view can check the state of the game before returning other players&#x27; cards, for example only once a showdown has started.</li>
<li class=""><strong>Hide other kinds of information.</strong> The same pattern hides units under fog of war, or a hidden role in a social deduction game: keep the data in a private table, and return only what the caller may see from a view. To send each player only what&#x27;s near them, without hiding anything, see <a class="" href="/docs/how-to/games/sync-nearby-entities">Only sync what&#x27;s near the player</a>.</li>
<li class=""><strong>Take turns.</strong> See <a class="" href="/docs/how-to/games/turn-based-game">Make a turn-based game with turn timeouts</a>.</li>
</ul>
<p>To learn more about the features used here, see <a class="" href="/docs/tables/access-permissions">Access Permissions</a> and <a class="" href="/docs/functions/views">Views</a>.</p>
