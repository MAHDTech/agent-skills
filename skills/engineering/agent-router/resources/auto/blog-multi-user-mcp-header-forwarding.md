<p>When teams first deploy MCP servers in production, the path of least resistance is a shared service account: one API token for Jira, one for Slack, one for GitHub — stored as Kubernetes Secrets and used for every request, regardless of who triggered the agent. This works until it doesn&#x27;t. Comments post under the wrong name, users see data their own accounts can&#x27;t access, and the RBAC rules carefully configured in your enterprise tools are silently bypassed.</p>
<p>Envoy AI Gateway ships per-backend header forwarding in the <code>MCPRoute</code> API — available since v0.6 and part of the now-GA v1.0 — which solves this for a common enterprise case with a single YAML addition. This post covers how it works, how it plays out in a real production deployment, and — just as important — when you should reach for OAuth or token exchange instead.</p>
<h2 class="anchor anchorTargetStickyNavbar_Vzrq" id="the-problem-with-shared-service-accounts">The Problem with Shared Service Accounts<a href="#the-problem-with-shared-service-accounts" class="hash-link" aria-label="Direct link to The Problem with Shared Service Accounts" title="Direct link to The Problem with Shared Service Accounts" translate="no">​</a></h2>
<p>Consider an internal agent platform routing dozens of concurrent agents through Envoy AI Gateway, each serving a different engineer or SRE. With a shared Jira service account, every agent has the same access regardless of the triggering user&#x27;s actual permissions. Slack tools can reach channels the triggering engineer isn&#x27;t a member of. Jira comments appear under the service account&#x27;s name, not the engineer&#x27;s. Nothing is technically broken — and that is the problem. The permission model of every downstream tool is being quietly flattened into "whatever the bot can do."</p>
<p>The instinct is to reach for OAuth. The reality is more nuanced, and it helps to first untangle what "authentication" actually means in an MCP deployment.</p>
<h2 class="anchor anchorTargetStickyNavbar_Vzrq" id="who-authenticates-what-the-two-questions">Who Authenticates What: The Two Questions<a href="#who-authenticates-what-the-two-questions" class="hash-link" aria-label="Direct link to Who Authenticates What: The Two Questions" title="Direct link to Who Authenticates What: The Two Questions" translate="no">​</a></h2>
<p>Every multi-user MCP setup has to answer two <em>separate</em> questions, and most confusion comes from mixing them together:</p>
\<ol\>
<li class=""><strong>Does the gateway trust the incoming request?</strong> — the front door.</li>
<li class=""><strong>Whose name does the backend tool see?</strong> — what happens inside.</li>
</ol>
<p>The first question is perimeter authentication. The gateway should verify that a request comes from someone (or something) in your organization before doing anything else. Envoy AI Gateway supports this through the <code>MCPRoute</code> security policy (API key or OAuth) or Envoy Gateway&#x27;s <code>SecurityPolicy</code> (OIDC/JWT). You want this in production regardless of everything below.</p>
<p>The second question is where multi-user identity lives. Once a request is inside, each backend MCP server needs <em>a</em> credential — and each backend decides what the caller can see based on <em>who that credential says they are</em>. There are four answers, and each is right for a different situation:</p>
\<ul\>
<li class=""><strong>A shared service account.</strong> The backend sees the same bot identity for every user. Right when the tool has no meaningful per-user permissions — a weather API, a public docs search. Wrong everywhere RBAC matters.</li>
<li class=""><strong>Forward the user&#x27;s own credential.</strong> The user already holds a credential the backend accepts — a personal access token, or a corporate SSO token for internal tools. The gateway passes it through, and the backend sees the actual user. This is the pattern this post covers.</li>
<li class=""><strong>The agent as its own identity.</strong> A nightly automation that files summary tickets shouldn&#x27;t impersonate anyone — it should <em>be</em> a machine identity with narrow, fixed permissions (OAuth client credentials). Right for headless automation acting on its own behalf.</li>
<li class=""><strong>Token exchange (RFC 8693).</strong> The user&#x27;s corporate token means nothing to an external SaaS on a different identity provider. A token service exchanges it for a downstream token that still represents the same user. Right for per-user identity <em>across</em> an IdP boundary — at the cost of real infrastructure.</li>
</ul>
<p>There is also the full OAuth authorization code flow with browser consent, which the MCP specification mandates for interactive clients talking to external servers. It is the right answer when a human is present — and architecturally impossible for a headless agent firing at 3am with no browser.</p>

<h2 class="anchor anchorTargetStickyNavbar_Vzrq" id="how-header-forwarding-works">How Header Forwarding Works<a href="#how-header-forwarding-works" class="hash-link" aria-label="Direct link to How Header Forwarding Works" title="Direct link to How Header Forwarding Works" translate="no">​</a></h2>
<p>The key design property is what <em>doesn&#x27;t</em> happen: Envoy AI Gateway&#x27;s MCP proxy builds a fresh HTTP request for every upstream call. Client headers do not propagate to backend MCP servers by default — at all. Forwarding is an explicit, per-backend opt-in via <code>forwardHeaders</code> on each backend reference.</p>
<p><img decoding="async" loading="lazy" alt="Fan-out with per-backend header scoping" src="/assets/images/multi-user-mcp-fanout-7d45f5ff9c2e7ca2ec996bc4c0172c30.png" width="1282" height="570" class="img_ev3q"></p>
<p>This matters most during fan-out. A single <code>tools/list</code> call fans out to every backend in the route, but each backend receives only the headers it explicitly opted into. A per-user Atlassian token configured for the Atlassian backend is never seen by any other backend in the same route. The absence of <code>forwardHeaders</code> on a backend means no identity propagation to that service, full stop.</p>
<p>Each entry can also rename the header on the way through: <code>name</code> selects the inbound header, and an optional <code>backendHeader</code> sets the name used toward the backend — useful when a backend expects a vendor-specific header.</p>
<h2 class="anchor anchorTargetStickyNavbar_Vzrq" id="level-1-pat-passthrough--zero-infrastructure">Level 1: PAT Passthrough — Zero Infrastructure<a href="#level-1-pat-passthrough--zero-infrastructure" class="hash-link" aria-label="Direct link to Level 1: PAT Passthrough — Zero Infrastructure" title="Direct link to Level 1: PAT Passthrough — Zero Infrastructure" translate="no">​</a></h2>

<p>The rename is also how per-user identity and a service-account credential coexist on one backend: forward the user&#x27;s token under a dedicated header while the backend&#x27;s <code>securityPolicy</code> injects the service credential into <code>Authorization</code>. Note that credentials injected by a backend <code>securityPolicy</code> are applied at the Envoy layer and overwrite any forwarded header of the same name — so give the forwarded user identity its own header rather than expecting it to take precedence.</p>
<p>Two honest caveats. First, in this mode the gateway is not validating the PATs — the backend is. Keep inbound authentication at the front door (an <code>MCPRoute</code> security policy, or OIDC at the gateway) so the gateway itself is never an open proxy. Second, forward identity headers only to backends inside your trust perimeter; if a backend cannot validate the credential, it has no business receiving it.</p>
<h2 class="anchor anchorTargetStickyNavbar_Vzrq" id="level-2-oidc--jwt-forwarding--the-same-idp-pattern">Level 2: OIDC + JWT Forwarding — The Same-IdP Pattern<a href="#level-2-oidc--jwt-forwarding--the-same-idp-pattern" class="hash-link" aria-label="Direct link to Level 2: OIDC + JWT Forwarding — The Same-IdP Pattern" title="Direct link to Level 2: OIDC + JWT Forwarding — The Same-IdP Pattern" translate="no">​</a></h2>

This is the natural hardening step for internal tools that natively validate your corporate identity.</p>
<h2 class="anchor anchorTargetStickyNavbar_Vzrq" id="stateless-passthrough-vs-token-broker">Stateless Passthrough vs. Token Broker<a href="#stateless-passthrough-vs-token-broker" class="hash-link" aria-label="Direct link to Stateless Passthrough vs. Token Broker" title="Direct link to Stateless Passthrough vs. Token Broker" translate="no">​</a></h2>
<p>Gateway products in this space often take a different approach: the user completes a consent flow or pastes a token once, the gateway stores it server-side, and clients afterwards just connect to a URL. It is fair to ask whether Envoy AI Gateway&#x27;s model — the client sends the credential on every request — is a step backwards.</p>
<p>It isn&#x27;t; it is a different point in the design space. Sending a credential per request is the normal model of HTTP authentication — every GitHub API call carries a token, every browser request carries cookies, and the MCP specification itself has clients send <code>Authorization</code> on each HTTP request. A broker doesn&#x27;t eliminate that; it moves the sending from client→backend to gateway→backend, and in exchange the gateway becomes a stateful token vault: encrypted storage, rotation, and a high-value breach target — with central revocation as the payoff.</p>
<p>Passthrough keeps the gateway stateless. There is nothing to steal at rest, nothing to rotate, and nothing to migrate; the credential rests with the client platform, which for an enterprise agent platform is typically already holding the user&#x27;s session. Short-lived, IdP-issued JWTs favor passthrough strongly. Long-lived tokens for external SaaS — where storage, refresh, and revocation genuinely need management — favor a broker or token exchange. The two models are complementary, and the same route can serve both.</p>
<h2 class="anchor anchorTargetStickyNavbar_Vzrq" id="what-this-looks-like-in-practice">What This Looks Like in Practice<a href="#what-this-looks-like-in-practice" class="hash-link" aria-label="Direct link to What This Looks Like in Practice" title="Direct link to What This Looks Like in Practice" translate="no">​</a></h2>
<p>Picture a platform aggregating a dozen MCP backends behind one route — Jira, Confluence, Slack, GitHub Enterprise, and internal observability tools, collectively exposing well over a hundred tools. Enabling per-user identity for the backends that need it is a YAML addition to the existing <code>MCPRoute</code>. No OAuth app registrations, no token storage, no consent flows, no changes to the backends themselves.</p>
<p>The results are exactly what the RBAC model promises: Jira comments attribute to the triggering engineer, not a bot. Confluence and Jira queries return only what each engineer&#x27;s own account can see. Agents triggered by different engineers surface different data, matching each user&#x27;s actual permissions. And because forwarding is per-backend, the user tokens never touch the public-API backends sharing the same route.</p>
<h2 class="anchor anchorTargetStickyNavbar_Vzrq" id="whats-next">What&#x27;s Next<a href="#whats-next" class="hash-link" aria-label="Direct link to What&#x27;s Next" title="Direct link to What&#x27;s Next" translate="no">​</a></h2>
<p>Header forwarding covers the case where the user&#x27;s credential already works downstream. For the cross-IdP case — calling Atlassian Cloud or GitHub.com with per-user identity — RFC 8693 OAuth token exchange support is actively in review. Between the two, the gateway layer is becoming the natural place where agent traffic picks up the right identity for each tool it touches.</p>
