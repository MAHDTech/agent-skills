page</button></div><div class="theme-doc-markdown markdown">\<header\>\<h1\>Extension Fields</h1></header>
<p>The AI Gateway supports extension fields that allow you to specify unified or backend-specific parameters directly as inline fields in your OpenAI-compatible requests. These fields are applied during the translation process to the target backend&#x27;s native API format.</p>
<h2 class="anchor anchorTargetStickyNavbar_Vzrq" id="overview">Overview<a href="#overview" class="hash-link" aria-label="Direct link to Overview" title="Direct link to Overview" translate="no">​</a></h2>
<p>Extension fields enable you to:</p>
\<ul\>
<li class="">Use advanced backend-specific features not available in the OpenAI API</li>
<li class="">Use unified configuration fields that work across multiple providers not available in the OpenAI API</li>
</ul>
<h3 class="anchor anchorTargetStickyNavbar_Vzrq" id="vendor-extension-fields">Vendor Extension Fields<a href="#vendor-extension-fields" class="hash-link" aria-label="Direct link to Vendor Extension Fields" title="Direct link to Vendor Extension Fields" translate="no">​</a></h3>
<p>Vendor specific fields are specified as inline fields in your OpenAI request and are applied after the standard OpenAI-to-backend translation.</p>
<h3 class="anchor anchorTargetStickyNavbar_Vzrq" id="unified-extension-fields">Unified Extension Fields<a href="#unified-extension-fields" class="hash-link" aria-label="Direct link to Unified Extension Fields" title="Direct link to Unified Extension Fields" translate="no">​</a></h3>
<p>For thinking/reasoning capabilities, you can use a unified <code>thinking</code> field that automatically translates to the correct backend-specific format:</p>
\<ul\>
<li class=""><strong>GCP Vertex AI (Gemini)</strong>: Translates to <code>generationConfig.thinkingConfig</code></li>
<li class=""><strong>GCP Anthropic</strong>: Uses <code>thinking</code> field directly</li>
<li class=""><strong>AWS Bedrock</strong>: Uses <code>thinking</code> field directly</li>
</ul>
<p>This unified approach allows you to write provider-agnostic requests while still leveraging thinking capabilities.</p>

<h3 class="anchor anchorTargetStickyNavbar_Vzrq" id="using-eager-tool-input-streaming">Using Eager Tool Input Streaming<a href="#using-eager-tool-input-streaming" class="hash-link" aria-label="Direct link to Using Eager Tool Input Streaming" title="Direct link to Using Eager Tool Input Streaming" translate="no">​</a></h3>
<p>By default, Anthropic buffers each tool parameter value and validates it before emitting it to the stream. Setting <code>eager_input_streaming</code> on a tool makes the model stream that tool&#x27;s input as it is generated, so <code>tool_calls[].function.arguments</code> fragments start arriving sooner. This matches the per-token streaming behavior of OpenAI and most other backends.</p>

<p>The field is a tri-state. Omitting it defaults to buffered streaming, <code>true</code> enables eager streaming for that tool, and an explicit <code>false</code> also buffers but holds that even when the deprecated <code>fine-grained-tool-streaming-2025-05-14</code> beta header is present, which otherwise turns unset tools on.</p>
<p>How arguments are accumulated does not change: clients concatenate the <code>arguments</code> fragments exactly as before. What changes is the guarantee. With eager streaming the server no longer validates the fragments, so the accumulated string is not guaranteed to be valid JSON — a response ending with <code>finish_reason: "length"</code> can cut a parameter off midway. Guard the parse and handle failure rather than assuming it succeeds. See <a href="https://platform.claude.com/docs/en/agents-and-tools/tool-use/fine-grained-tool-streaming#accumulating-tool-input-deltas" target="_blank" rel="noopener noreferrer" class="">Accumulating tool input deltas</a>.</p>
