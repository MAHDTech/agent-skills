<h2 class="anchor anchorTargetStickyNavbar_Vzrq" id="overview">Overview<a href="#overview" class="hash-link" aria-label="Direct link to Overview" title="Direct link to Overview" translate="no">​</a></h2>
<p>Upstream Authentication secures the connectivity between the Gateway and the LLM Providers. This layer ensures secure communication and proper access control when the Gateway interacts with various AI service providers like AWS Bedrock, Azure OpenAI, Open AI, Mistral, Gemini, and other platforms.</p>
<h2 class="anchor anchorTargetStickyNavbar_Vzrq" id="why-upstream-authentication-matters">Why Upstream Authentication Matters<a href="#why-upstream-authentication-matters" class="hash-link" aria-label="Direct link to Why Upstream Authentication Matters" title="Direct link to Why Upstream Authentication Matters" translate="no">​</a></h2>
<p>Upstream Authentication is essential for several reasons:</p>
\<ol\>
<li class="">
<p><strong>Security Layer</strong>: It provides a secure authentication mechanism between the Gateway and upstream providers, preventing credentials sprawl across teams and organizations.</p>
</li>
<li class="">
<p><strong>Credential Management</strong>: It allows AI platform teams to handle the secure storage and management of credentials and use them in one place. This makes the revocation and rotation of credentials easier.</p>
</li>
<li class="">
<p><strong>Compliance</strong>: It helps organizations meet security and compliance requirements by maintaining proper authentication protocols and enforcing controlled usage of AI resources.</p>
</li>
</ol>
<h2 class="anchor anchorTargetStickyNavbar_Vzrq" id="enterprise-security-architecture">Enterprise Security Architecture<a href="#enterprise-security-architecture" class="hash-link" aria-label="Direct link to Enterprise Security Architecture" title="Direct link to Enterprise Security Architecture" translate="no">​</a></h2>
<p>In enterprise environments, security is implemented in multiple layers:</p>
\<ol\>
<li class="">
<p><strong>Client to Gateway Authentication</strong></p>
\<ul\>
<li class="">Clients must authenticate to the Gateway using appropriate methods (API keys, OAuth, etc.) aligned with the organization&#x27;s security standards.</li>
<li class="">This ensures only authorized clients can access the Gateway&#x27;s services, and the Gateway enforces the access to the upstream providers and models.</li>
</ul>

</li>
<li class="">
<p><strong>Gateway to Upstream Authentication</strong></p>
\<ul\>
<li class="">The Gateway must authenticate to upstream providers.</li>
<li class="">This layer is managed by Upstream Authentication.</li>
<li class="">Ensures secure communication between the Gateway and AI service providers.</li>
</ul>
</li>
</ol>

<h2 class="anchor anchorTargetStickyNavbar_Vzrq" id="credential-management">Credential Management<a href="#credential-management" class="hash-link" aria-label="Direct link to Credential Management" title="Direct link to Credential Management" translate="no">​</a></h2>
<p><strong>Where the providers support short lived access credentials</strong>, the Agent Router control plane supports automated credential management with the providers&#x27; identity system. This ensures a short-lived proof of authorization, such as an access token, is used when the request is sent to the upstream service.</p>
<p><strong>For providers that support long lived access credentials</strong>, the Agent Router control plane supports a manual credential management process. In these cases the credentials, like API keys, are stored in Kubernetes secrets and managed by the administrator.</p>
<h3 class="anchor anchorTargetStickyNavbar_Vzrq" id="automated-credential-management">Automated Credential Management<a href="#automated-credential-management" class="hash-link" aria-label="Direct link to Automated Credential Management" title="Direct link to Automated Credential Management" translate="no">​</a></h3>
<p>The Gateway integrates with each provider&#x27;s identity system to ensure secure, short-lived authentication:</p>
\<ul\>
<li class=""><strong>AWS Bedrock</strong>: Uses OIDC integration with AWS STS to generate temporary credentials for each request</li>
<li class=""><strong>Azure OpenAI</strong>: Leverages Entra ID (formerly Azure AD) to provide short-lived access tokens</li>
<li class=""><strong>GCP VertexAI</strong>: Uses GCP workload federation with Google STS to generate temporary credentials for each request</li>
</ul>
<p>In both cases, the Gateway automatically manages these credentials, ensuring that each request to upstream providers is sent with short-lived credentials. This approach significantly reduces the risk of credential exposure and aligns with enterprise security best practices.</p>
<div class="theme-admonition theme-admonition-info admonition_xJq3 alert alert--info"><div class="admonitionHeading_Gvgb"><span class="admonitionIcon_Rf37"><svg viewBox="0 0 14 16"><path fill-rule="evenodd" d="M7 2.3c3.14 0 5.7 2.56 5.7 5.7s-2.56 5.7-5.7 5.7A5.71 5.71 0 0 1 1.3 8c0-3.14 2.56-5.7 5.7-5.7zM7 1C3.14 1 0 4.14 0 8s3.14 7 7 7 7-3.14 7-7-3.14-7-7-7zm1 3H6v5h2V4zm0 6H6v2h2v-2z"></path></svg></span>info</div><div class="admonitionContent_BuS1"><p>Learn more about connecting to <a class="" href="/docs/getting-started/connect-providers/aws-bedrock">AWS Bedrock</a> and <a class="" href="/docs/getting-started/connect-providers/azure-openai">Azure OpenAI</a> in the provider specific documentation.</p></div></div>
<h3 class="anchor anchorTargetStickyNavbar_Vzrq" id="manual-credential-management">Manual Credential Management<a href="#manual-credential-management" class="hash-link" aria-label="Direct link to Manual Credential Management" title="Direct link to Manual Credential Management" translate="no">​</a></h3>
<p>For providers that support long lived access credentials, the Agent Router control plane supports a manual credential management process. In these cases the credentials, like API keys, are stored in Kubernetes secrets and managed by the AI Gateway administrator. Agent Router will use the credentials from the secret to authenticate with the upstream service, attaching them to each request by securely retrieving them from the secret and attaching them to the request.</p>
<div class="theme-admonition theme-admonition-info admonition_xJq3 alert alert--info"><div class="admonitionHeading_Gvgb"><span class="admonitionIcon_Rf37"><svg viewBox="0 0 14 16"><path fill-rule="evenodd" d="M7 2.3c3.14 0 5.7 2.56 5.7 5.7s-2.56 5.7-5.7 5.7A5.71 5.71 0 0 1 1.3 8c0-3.14 2.56-5.7 5.7-5.7zM7 1C3.14 1 0 4.14 0 8s3.14 7 7 7 7-3.14 7-7-3.14-7-7-7zm1 3H6v5h2V4zm0 6H6v2h2v-2z"></path></svg></span>info</div><div class="admonitionContent_BuS1"><p>Learn more about connecting to <a class="" href="/docs/getting-started/connect-providers/openai">OpenAI</a> and adding your API key to the secret. You can use the same approach for other providers that support long lived credentials.</p></div></div>
<h2 class="anchor anchorTargetStickyNavbar_Vzrq" id="per-request-credential-override">Per-Request Credential Override<a href="#per-request-credential-override" class="hash-link" aria-label="Direct link to Per-Request Credential Override" title="Direct link to Per-Request Credential Override" translate="no">​</a></h2>
<p>By default, a <code>BackendSecurityPolicy</code> attaches one credential to every request. The optional
<code>credentialOverride</code> field instead lets a trusted filter that runs ahead of the AI Gateway
processor — typically an external authorization service wired in via <code>ext_authz</code> — supply the
upstream credential for each request individually. This is how a multi-tenant gateway can bill
every tenant against their own provider account while still sharing routes and backends.</p>
<p>The per-request credential can come from one of two sources.</p>
<h3 class="anchor anchorTargetStickyNavbar_Vzrq" id="from-dynamic-metadata-recommended">From Dynamic Metadata (recommended)<a href="#from-dynamic-metadata-recommended" class="hash-link" aria-label="Direct link to From Dynamic Metadata (recommended)" title="Direct link to From Dynamic Metadata (recommended)" translate="no">​</a></h3>

<p>The declared namespaces apply to all AI traffic of the Gateways referencing the config. The list
is deliberately not derived from the policies that read it: a <code>BackendSecurityPolicy</code> is namespaced
and can be written by a backend owner, while what Envoy hands to the external processor is the
Gateway owner&#x27;s decision. Envoy forwards exactly what that owner declared, so a policy naming an
undeclared namespace behaves as if the metadata were absent, and the controller logs an error
naming it. The declaration governs the Gateway that makes it, so attaching a route to a Gateway
cannot widen what a different Gateway forwards. An external authorization service produces the
metadata through the <code>dynamic_metadata</code> field of its <code>CheckResponse</code>.</p>

A filter that writes the credential as typed metadata
(a <code>google.protobuf.Any</code> under the same namespace) produces no value, and the request falls back
to the static credential or is rejected according to <code>fallbackToConfigured</code>.</p><p>A policy reads a namespace Envoy forwards into the processor. <code>io.envoy.ai_gateway</code> travels the
other way: the processor writes it and Envoy receives it, for token-based rate limiting and
access logs.</p></div></div>
<p>Dynamic metadata is the recommended source. Clients cannot forge it, since only filters in the
gateway&#x27;s own configuration can write it. And because the credential never appears as a request
header, there is nothing to strip, nothing for access logs to capture, and nothing that can
reach another backend on retries or fallback.</p>
<h3 class="anchor anchorTargetStickyNavbar_Vzrq" id="from-request-headers">From Request Headers<a href="#from-request-headers" class="hash-link" aria-label="Direct link to From Request Headers" title="Direct link to From Request Headers" translate="no">​</a></h3>
<p>Alternatively, the trusted filter can inject the credential as a request header, which the
gateway reads and strips before forwarding the request to the backend it authenticated:</p>
<div class="language-yaml codeBlockContainer_Ckt0 theme-code-block" style="--prism-color:#393A34;--prism-background-color:#f6f8fa"><div class="codeBlockContent_QJqH"><pre tabindex="0" class="prism-code language-yaml codeBlock_bY9V thin-scrollbar" style="color:#393A34;background-color:#f6f8fa"><code class="codeBlockLines_e6Vv"><div class="token-line" style="color:#393A34"><span class="token plain">  </span><span class="token key atrule" style="color:#00a4db">credentialOverride</span><span class="token punctuation" style="color:#393A34">:</span><span class="token plain"></span><br></div><div class="token-line" style="color:#393A34"><span class="token plain">    </span><span class="token key atrule" style="color:#00a4db">fromRequestHeaders</span><span class="token punctuation" style="color:#393A34">:</span><span class="token plain"> </span><span class="token punctuation" style="color:#393A34">{</span><span class="token punctuation" style="color:#393A34">}</span><span class="token plain"> </span><span class="token comment" style="color:#999988;font-style:italic"># reads x-aigw-api-key for type: APIKey</span><br></div></code></pre></div></div>
<p>Because any client can set request headers, this source is only safe when the trusted boundary
overwrites or rejects client-supplied values of the configured header. The header also travels
with the request through the filter chain, and stripping is configured per backend — so on
routes with multiple backends (for example provider fallback), prefer <code>fromDynamicMetadata</code>,
which has neither exposure.</p>
<h3 class="anchor anchorTargetStickyNavbar_Vzrq" id="fallback-behaviour">Fallback Behaviour<a href="#fallback-behaviour" class="hash-link" aria-label="Direct link to Fallback Behaviour" title="Direct link to Fallback Behaviour" translate="no">​</a></h3>
<p><code>fallbackToConfigured</code> (default <code>true</code>) controls what happens when the source carries no
credential: fall back to the static credential configured in the policy, or, when set to
<code>false</code>, reject the request with a 401 without contacting the provider. A <em>partial</em> AWS
credential — an access key ID without a secret access key, or the reverse — always fails the
request rather than falling back, since it indicates a misconfigured credential producer.</p>
<p>Falling back requires something to fall back <em>to</em>: if the policy has no static credential —
for example <code>GCPCredentials</code> relying on Application Default Credentials with no credentials
file or workload identity federation — the controller rejects <code>credentialOverride</code> unless
<code>fallbackToConfigured: false</code> is set explicitly.</p>
<p>When enabling <code>fromDynamicMetadata</code> on a backend already serving traffic, prefer starting with
<code>fallbackToConfigured: true</code> and tightening to <code>false</code> afterwards: the processor configuration
and Envoy&#x27;s forwarding configuration are delivered on separate channels, and with <code>false</code> a
request that lands in between is rejected with a 401.</p>

It ensures secure communication between the Gateway and upstream AI service providers while supporting modern authentication methods and enterprise security requirements.
