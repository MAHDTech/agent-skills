<!-- -->
<p>SpacetimeDB allows you to easily access authentication (auth) claims embedded in
OIDC-compliant JWT tokens. Auth claims are key-value pairs that provide
information about the authenticated user. For example, they may contain a user&#x27;s
unique ID, email, or authentication provider. If you want to view these fields
for yourself, you can inspect the contents of any JWT using online tools like <a href="https://jwt.io/" target="_blank" rel="noopener noreferrer" class="">jwt.io</a>.</p>
<p>Within a SpacetimeDB reducer, you can access the auth claims from a client&#x27;s
token via the <code>ReducerContext</code>. Below are some examples of how to use these claims.</p>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="accessing-common-claims-subject-and-issuer">Accessing Common Claims: Subject and Issuer<a href="#accessing-common-claims-subject-and-issuer" class="hash-link" aria-label="Direct link to Accessing Common Claims: Subject and Issuer" title="Direct link to Accessing Common Claims: Subject and Issuer" translate="no">​</a></h2>
<p>The subject (<code>sub</code>) and issuer (<code>iss</code>) are the most commonly accessed claims in
a JWT. The issuer indicates which authentication provider issued the token, and
the subject represents the unique identifier assigned to the user by the issuer.
These are required claims, which are used to compute each user&#x27;s <code>Identity</code>.
Because these are so commonly used, there are helper functions to get them.</p>

<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="example-restricting-auth-providers">Example: Restricting auth providers<a href="#example-restricting-auth-providers" class="hash-link" aria-label="Direct link to Example: Restricting auth providers" title="Direct link to Example: Restricting auth providers" translate="no">​</a></h2>
<p>Since users can use any valid token to connect to SpacetimeDB, their token may originate from any authentication provider. For example, they could send an OIDC compliant token from GitHub even though you only want to accept tokens from Google. It often makes sense to restrict access to your module to users issued by your own issuer or specific issuers. It is best practice to check at least the issuer when clients connect, so you can ensure that your data can only be accessed by users of your application.</p>
<p>Additionally, it&#x27;s imperative that you check the <code>aud</code> claim to ensure the issuer intended your application to receive the token. This ensures that applications which send you the token, cannot repurpose tokens issued for use with another application.</p>
<p>For example, we can restrict access to clients with SpacetimeAuth credentials.</p>
