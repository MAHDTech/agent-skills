class="theme-doc-markdown markdown">\<header\>\<h1\>Environment Variables</h1></header>
<p>Environment variables store configuration and secrets for a database, such as API keys and deployment settings. A module declares the names it reads and any allowed values. Publishing preserves stored values unless you explicitly replace or delete them. Undeclared values can be stored before a module starts using them. Module code reads them through <code>ctx.env</code>, or <code>ctx.Env</code> in C#.</p>
<p>Use environment-only publishing to change configuration without uploading a module. Use a <a href="#dynamically-editable-or-untyped-secrets" class="">private table</a> when module code must edit values or read arbitrary keys.</p>
<p>This guide assumes a module set up using a quickstart, such as the <a class="" href="/docs/quickstarts/rust">Rust quickstart</a>, and familiarity with <a class="" href="/docs/databases/building-publishing">publishing</a>.</p>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="declare-and-read-variables">Declare and read variables<a href="#declare-and-read-variables" class="hash-link" aria-label="Direct link to Declare and read variables" title="Direct link to Declare and read variables" translate="no">​</a></h2>
<p>Declare every environment key the module reads. All values are strings. A declaration can accept any string, one exact string, or a set of allowed strings. Optional declarations permit an absent value.</p>
<p>These examples declare a required <code>API_KEY</code>, a required <code>MODE</code> restricted to <code>development</code> or <code>production</code>, and an optional <code>LOG_LEVEL</code> restricted to <code>info</code> or <code>debug</code>.</p>

<p>With a local server running on port 3000, publish from the directory containing that configuration. This example uses a disposable development value:</p>
<pre tabindex="0" class="codeBlockStandalone_LlrK thin-scrollbar codeBlockContainer_hFbQ theme-code-block" style="--prism-color:#bfc7d5;--prism-background-color:#292d3e"><code class="codeBlockLines_JqGU"><span class="line"><span style="color:#BD93F9">API_KEY</span><span style="color:#FF79C6">=</span><span style="color:#E9F284">&#x27;</span><span style="color:#F1FA8C">development-only-key</span><span style="color:#E9F284">&#x27;</span><span style="color:#50FA7B"> spacetime</span><span style="color:#F1FA8C"> publish</span><span style="color:#BD93F9"> --server</span><span style="color:#F1FA8C"> http://127.0.0.1:3000</span></span></code></pre>
<p>For an existing database, you can enter credentials once through its website settings and reuse them on later publishes. For initial publishing, supply the value through the publishing process&#x27;s environment, <code>spacetime.local.json</code>, or <code>spacetime.{environment}.local.json</code>. Keep checked-in <code>spacetime.json</code> and <code>spacetime.{environment}.json</code> limited to non-secret defaults. Ensure the local files are ignored by Git:</p>
<div class="language-gitignore codeBlockContainer_hFbQ theme-code-block" style="--prism-color:#bfc7d5;--prism-background-color:#292d3e"><div class="codeBlockContent_VOyQ"><pre tabindex="0" class="prism-code language-gitignore codeBlock_evfK thin-scrollbar" style="color:#bfc7d5;background-color:#292d3e"><code class="codeBlockLines_JqGU"><span class="token-line" style="color:#bfc7d5"><span class="token plain">spacetime.local.json</span><br></span><span class="token-line" style="color:#bfc7d5"><span class="token plain">spacetime.*.local.json</span><br></span></code></pre></div></div>
<p>The <code>.local</code> naming convention does not itself prevent a file from being committed.</p>
<p>Publishing uses the first available value for each declared key in this order:</p>
\<ol\>
<li class="">A value in the publishing process&#x27;s environment.</li>
<li class="">A value in the resolved configuration&#x27;s <code>env</code> map.</li>
<li class="">The stored database value, unless <code>--replace-env</code> is specified.</li>
<li class="">Absence, which is accepted only for an optional declaration.</li>
</ol>
<p>A shell value overrides JSON even when it is an empty string or the key is absent from JSON. Already-exported variables behave the same as inline assignments. Unrelated shell variables are ignored unless the module declares their names. The CLI displays supplied key names and their sources, without printing their values.</p>
<p>The configuration files <code>spacetime.json</code>, <code>spacetime.local.json</code>, <code>spacetime.{environment}.json</code>, and <code>spacetime.{environment}.local.json</code> apply in increasing precedence, where <em>environment</em> is the environment selected with <code>--env</code>. Their <code>env</code> maps merge by key, as do maps inherited by child database targets. A higher-precedence value replaces that key while preserving unrelated keys. An empty map does not erase inherited keys.</p>
<p>JSON strings pass through unchanged. Booleans and numbers are converted to strings, so <code>false</code> supplies <code>"false"</code>; declarations still validate strings. Use JSON strings when exact numeric spelling matters. Arrays, objects, and <code>null</code> are rejected. Explicit JSON keys the module has not declared are accepted as stored strings; module code cannot read them. A matching shell variable is not forwarded until the key is declared. An invalid effective value rejects the publish rather than falling back to a lower-precedence value. Omitting an optional key preserves any stored value. To clear it, use <code>--unset-env</code> and remove it from effective JSON and shell inputs. An empty string is a value, not a deletion instruction.</p>
<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="preserve-edit-or-replace-values">Preserve, edit, or replace values<a href="#preserve-edit-or-replace-values" class="hash-link" aria-label="Direct link to Preserve, edit, or replace values" title="Direct link to Preserve, edit, or replace values" translate="no">​</a></h3>
<p>After a successful publish, every required declaration has a stored value, and every present declared value satisfies its constraint. Publishing validates the resulting environment atomically before initialization or migration. You can supply a replacement value in the same publish that changes its declaration. Failure leaves the previous module and values unchanged.</p>
<p>An ordinary publish retains unspecified values, including values whose declarations were removed. You can explicitly supply undeclared keys in JSON or through website editing before deploying a declaration. Later publishing validates those stored strings against the new declaration. Removing a declaration does not delete its value, but module reads of that key then fail.</p>
<p>Update an existing database without building or uploading a module:</p>
<pre tabindex="0" class="codeBlockStandalone_LlrK thin-scrollbar codeBlockContainer_hFbQ theme-code-block" style="--prism-color:#bfc7d5;--prism-background-color:#292d3e"><code class="codeBlockLines_JqGU"><span class="line"><span style="color:#BD93F9">API_KEY</span><span style="color:#FF79C6">=</span><span style="color:#E9F284">&#x27;</span><span style="color:#F1FA8C">development-only-replacement</span><span style="color:#E9F284">&#x27;</span><span style="color:#50FA7B"> spacetime</span><span style="color:#F1FA8C"> publish</span><span style="color:#F1FA8C"> env-example</span><span style="color:#BD93F9"> --env-only</span><span style="color:#BD93F9"> --server</span><span style="color:#F1FA8C"> http://127.0.0.1:3000</span></span></code></pre>
<p>This uses the deployed schema for declared shell overrides and accepts explicit JSON values for undeclared keys. It does not run initialization or migration. A stale module version rejects the request; refresh and retry. For a new database, supply required values together with the initial module publish so they are available in <code>init</code>.</p>
<p>Delete an optional or undeclared value explicitly, after removing it from effective JSON and shell inputs:</p>
<pre tabindex="0" class="codeBlockStandalone_LlrK thin-scrollbar codeBlockContainer_hFbQ theme-code-block" style="--prism-color:#bfc7d5;--prism-background-color:#292d3e"><code class="codeBlockLines_JqGU"><span class="line"><span style="color:#50FA7B">spacetime</span><span style="color:#F1FA8C"> publish</span><span style="color:#F1FA8C"> env-example</span><span style="color:#BD93F9"> --env-only</span><span style="color:#BD93F9"> --unset-env</span><span style="color:#F1FA8C"> LOG_LEVEL</span><span style="color:#BD93F9"> --server</span><span style="color:#F1FA8C"> http://127.0.0.1:3000</span></span></code></pre>
<p>Deleting a required value is rejected. Repeat <code>--unset-env</code> to delete multiple keys. To replace the entire store with the supplied values, use <code>--replace-env</code> with either normal publishing or <code>--env-only</code>. Replacement deletes every omitted declared and undeclared key, and fails atomically if required values are missing. It cannot be combined with <code>--unset-env</code>.</p>
<p>The destructive <code>--delete-data</code> operation still clears all database data, including environment values. Supply required secrets again when resetting a database. <code>--env-only</code> cannot be combined with a reset.</p>
<p>The same preservation rules apply to precompiled modules published with <code>--bin-path</code>. The CLI reads declarations from the artifact being published. HTTP clients and module procedures can use the <a class="" href="/docs/http/database#publishing-with-environment-values">HTTP publish format</a>; project configuration and shell overrides are CLI conveniences.</p>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="inspect-published-values">Inspect published values<a href="#inspect-published-values" class="hash-link" aria-label="Direct link to Inspect published values" title="Direct link to Inspect published values" translate="no">​</a></h2>
<p>The database owner and collaborators with private-table read access can inspect the environment. For the local database above:</p>
<pre tabindex="0" class="codeBlockStandalone_LlrK thin-scrollbar codeBlockContainer_hFbQ theme-code-block" style="--prism-color:#bfc7d5;--prism-background-color:#292d3e"><code class="codeBlockLines_JqGU"><span class="line"><span style="color:#50FA7B">spacetime</span><span style="color:#F1FA8C"> env</span><span style="color:#F1FA8C"> list</span><span style="color:#F1FA8C"> env-example</span><span style="color:#BD93F9"> --server</span><span style="color:#F1FA8C"> http://127.0.0.1:3000</span></span>
<span class="line"><span style="color:#50FA7B">spacetime</span><span style="color:#F1FA8C"> env</span><span style="color:#F1FA8C"> get</span><span style="color:#F1FA8C"> env-example</span><span style="color:#F1FA8C"> MODE</span><span style="color:#BD93F9"> --server</span><span style="color:#F1FA8C"> http://127.0.0.1:3000</span></span></code></pre>
<p><code>env list</code> prints a table of keys and values. <code>env get</code> prints the requested value and fails if it is absent. Both are explicit inspection commands and include secrets in their output. Automatic publish output still omits values.</p>
<p>Values are stored in the private system table <code>st_env</code>. Authorized SQL reads are also supported:</p>
<pre tabindex="0" class="codeBlockStandalone_LlrK thin-scrollbar codeBlockContainer_hFbQ theme-code-block" style="--prism-color:#bfc7d5;--prism-background-color:#292d3e"><code class="codeBlockLines_JqGU"><span class="line"><span style="color:#FF79C6">SELECT</span><span style="color:#FF79C6"> key</span><span style="color:#FF79C6"> FROM</span><span style="color:#F8F8F2"> st_env;</span></span>
<span class="line"><span style="color:#FF79C6">SELECT</span><span style="color:#FF79C6"> value</span><span style="color:#FF79C6"> FROM</span><span style="color:#F8F8F2"> st_env </span><span style="color:#FF79C6">WHERE</span><span style="color:#FF79C6"> key</span><span style="color:#FF79C6"> =</span><span style="color:#E9F284"> &#x27;</span><span style="color:#F1FA8C">MODE</span><span style="color:#E9F284">&#x27;</span><span style="color:#F8F8F2">;</span></span></code></pre>
<p>SQL writes to <code>st_env</code>, module-side writes, and separate CLI setters are not supported. Changes go through a validated module or environment-only publish.</p>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="access-and-limits">Access and limits<a href="#access-and-limits" class="hash-link" aria-label="Direct link to Access and limits" title="Direct link to Access and limits" translate="no">​</a></h2>
<p>Publishing environment values uses the same permission as publishing the module. This includes Developer-role collaborators where they can publish modules. Environment changes add no separate Admin requirement; a destructive reset or container configuration change still requires its normal permissions.</p>
<p>Reducers, procedures, views, and HTTP handlers entered by the host in the root module can read its declared environment. Host-dispatched submodule entry points cannot read it, and submodules cannot declare a nonempty environment. There is no separate environment-variable namespace to configure for a submodule. A module with environment declarations can be published independently as a root module, but cannot be included as a submodule with those declarations. See <a class="" href="/docs/submodules">Submodules</a> for this restriction. Ordinary helper calls retain their calling entry point&#x27;s access, including helpers defined in libraries or submodules. Root code can also pass a value to a helper explicitly.</p>
<p>A procedure suspended across a publish cannot read values belonging to a replacement program. Environment reads in views participate in dependency tracking, so publishing changed values refreshes affected views. Module code remains responsible for what it returns or logs: returning a secret from a public view exposes that value to clients.</p>
<p>Keys must match <code>[A-Za-z_][A-Za-z0-9_]*</code>. The limits are 256 bytes per key, 8 KiB per value, 256 declarations per database, and 256 stored values including undeclared keys. Length limits count UTF-8 bytes. Values may be empty if their declaration accepts an empty string.</p>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="dynamically-editable-or-untyped-secrets">Dynamically editable or untyped secrets<a href="#dynamically-editable-or-untyped-secrets" class="hash-link" aria-label="Direct link to Dynamically editable or untyped secrets" title="Direct link to Dynamically editable or untyped secrets" translate="no">​</a></h2>
<p>Use an ordinary <a class="" href="/docs/tables/access-permissions">private table</a> when module code must edit secrets or read keys without declaring them. For example, a table with a string primary-key column and a string value column can store arbitrary secret names and values. The table itself still has typed columns; its individual keys need no environment declarations or constraints.</p>
<p>Update that table through reducers that explicitly authorize the caller. Keeping a table private controls direct client reads; it does not authorize calls to a reducer that modifies or returns its contents. Apply the same care to views, procedure results, and logs. Private tables follow the database&#x27;s normal private-table permissions, including administrative reads.</p>
