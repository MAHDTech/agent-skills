<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="-safe-changes-always-allowed">✅ Safe Changes (Always Allowed)<a href="#-safe-changes-always-allowed" class="hash-link" aria-label="Direct link to ✅ Safe Changes (Always Allowed)" title="Direct link to ✅ Safe Changes (Always Allowed)" translate="no">​</a></h2>
<p>The following changes are always allowed and will not break existing clients:</p>
\<ul\>
<li class=""><strong>Adding new tables.</strong> Non-updated clients will not be able to see them.</li>
<li class=""><strong>Adding indexes.</strong></li>
<li class=""><strong>Adding or removing <code>Auto Inc</code> annotations.</strong></li>
<li class=""><strong>Changing tables from private to public.</strong></li>
<li class=""><strong>Adding new reducers.</strong></li>
<li class=""><strong>Removing <code>Unique</code> constraints.</strong></li>
</ul>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="️-potentially-breaking-changes">⚠️ Potentially Breaking Changes<a href="#️-potentially-breaking-changes" class="hash-link" aria-label="Direct link to ⚠️ Potentially Breaking Changes" title="Direct link to ⚠️ Potentially Breaking Changes" translate="no">​</a></h2>
<p>These changes are allowed by automatic migration, but may cause runtime errors for clients that haven&#x27;t been updated:</p>
\<ul\>
<li class="">
<p><strong>Adding new columns to the end of a table with a default value.</strong> The new column must be added at the end of the table definition and must have a default value specified. Non-updated clients will not be aware of the new column.</p>
</li>
<li class="">
<p><strong>Changing or removing reducers.</strong> Clients attempting to call the old version of a changed reducer or a removed reducer will receive runtime errors.</p>
</li>
<li class="">
<p><strong>Changing tables from public to private.</strong> Clients subscribed to a newly-private table will receive runtime errors.</p>
</li>
<li class="">
<p><strong>Changing table or column accessor names while preserving canonical names.</strong> The stored data can be migrated, but source code that refers to the old accessors must be updated.</p>
</li>
<li class="">
<p><strong>Removing empty tables.</strong> SpacetimeDB can remove a table only if it has no rows. Removing a table disconnects active clients. Clients using bindings or subscription queries generated from the old schema must be updated before reconnecting, because the removed table no longer exists.</p>
</li>
<li class="">
<p><strong>Removing <code>Primary Key</code> annotations.</strong> Non-updated clients will still use the old primary key as a unique key in their local cache, which can result in non-deterministic behavior when updates are received.</p>
</li>
<li class="">
<p><strong>Removing indexes.</strong> This is only breaking in specific situations. The main issue occurs with subscription queries involving semijoins, such as:</p>
<pre tabindex="0" class="codeBlockStandalone_LlrK thin-scrollbar codeBlockContainer_hFbQ theme-code-block" style="--prism-color:#bfc7d5;--prism-background-color:#292d3e"><code class="codeBlockLines_JqGU"><span class="line"><span style="color:#F8F8F2">tables.employee.</span><span style="color:#50FA7B">leftSemijoin</span><span style="color:#F8F8F2">(</span></span>
<span class="line"><span style="color:#F8F8F2">  tables.dept,</span></span>
<span class="line"><span style="color:#F8F8F2">  (</span><span style="color:#FFB86C;font-style:italic">employee</span><span style="color:#F8F8F2">, </span><span style="color:#FFB86C;font-style:italic">dept</span><span style="color:#F8F8F2">) </span><span style="color:#FF79C6">=></span><span style="color:#F8F8F2"> employee.deptName.</span><span style="color:#50FA7B">eq</span><span style="color:#F8F8F2">(dept.deptName)</span></span>
<span class="line"><span style="color:#F8F8F2">)</span></span></code></pre>
<p>For performance reasons, SpacetimeDB will only allow this kind of subscription query if there are indexes on both join columns (<code>Employee.DeptName</code> and <code>Dept.DeptName</code>). Removing either index will invalidate this subscription query, resulting in client-side runtime errors.</p>
</li>
</ul>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="-forbidden-changes">❌ Forbidden Changes<a href="#-forbidden-changes" class="hash-link" aria-label="Direct link to ❌ Forbidden Changes" title="Direct link to ❌ Forbidden Changes" translate="no">​</a></h2>
<p>The following changes cannot be performed with automatic migration and will cause the publish to fail:</p>
\<ul\>
<li class=""><strong>Removing non-empty tables.</strong> Empty tables can be removed automatically, but table removal fails if the existing table contains rows.</li>
<li class=""><strong>Removing or modifying existing columns.</strong> This includes changing the type, canonical name, or order of columns. Changing only the generated accessor alias is allowed, but source code that refers to the old accessor must be updated.</li>
<li class=""><strong>Adding columns without a default value.</strong> New columns must have a default value so existing rows can be populated.</li>
<li class=""><strong>Adding columns in the middle of a table.</strong> New columns must be added at the end of the table definition.</li>
<li class=""><strong>Changing whether a table is used for <code>scheduling</code>.</strong></li>
<li class=""><strong>Adding <code>Unique</code> or <code>Primary Key</code> constraints.</strong> This could result in existing tables being in an invalid state.</li>
<li class=""><strong>Changing an index accessor name.</strong> Automatic migration matches an existing index by its canonical name, so renaming only the generated accessor for that index is not supported. Add a separate index definition with the desired accessor, then update code to use the new accessor.</li>
</ul>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="working-with-forbidden-changes">Working with Forbidden Changes<a href="#working-with-forbidden-changes" class="hash-link" aria-label="Direct link to Working with Forbidden Changes" title="Direct link to Working with Forbidden Changes" translate="no">​</a></h2>
<p>If you need to make changes that aren&#x27;t supported by automatic migration, see <a class="" href="/docs/databases/incremental-migrations">Incremental Migrations</a> for a production-ready pattern that allows complex schema changes without downtime or data loss.</p>
<p>For development and testing, you can use <code>spacetime publish --delete-data</code> to completely reset your database, but this should <strong>not</strong> be used in production as it permanently deletes all data.</p>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="best-practices">Best Practices<a href="#best-practices" class="hash-link" aria-label="Direct link to Best Practices" title="Direct link to Best Practices" translate="no">​</a></h2>
<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="during-development">During Development<a href="#during-development" class="hash-link" aria-label="Direct link to During Development" title="Direct link to During Development" translate="no">​</a></h3>
\<ul\>
<li class="">Use <code>--delete-data</code> freely during early development when data loss is acceptable</li>
<li class="">Test migrations with sample data before applying to production databases</li>
<li class="">Consider creating separate databases for development, staging, and production</li>
</ul>
<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="for-production">For Production<a href="#for-production" class="hash-link" aria-label="Direct link to For Production" title="Direct link to For Production" translate="no">​</a></h3>
\<ul\>
<li class=""><strong>Plan schema changes carefully</strong> - Review the migration compatibility rules before making changes</li>
<li class=""><strong>Coordinate with client updates</strong> - When making potentially breaking changes, ensure clients are updated to handle the new schema</li>
<li class=""><strong>Use feature flags</strong> - When adding new functionality, consider using feature flags in your reducers to enable gradual rollouts</li>
<li class=""><strong>Maintain backwards compatibility</strong> - Where possible, add new tables/reducers rather than modifying existing ones</li>
<li class=""><strong>Document breaking changes</strong> - Keep a changelog of schema changes that may affect clients</li>
</ul>
<h3 class="anchor anchorTargetStickyNavbar_Y_NL" id="migration-strategies">Migration Strategies<a href="#migration-strategies" class="hash-link" aria-label="Direct link to Migration Strategies" title="Direct link to Migration Strategies" translate="no">​</a></h3>
<p>For complex schema changes that aren&#x27;t supported by automatic migration:</p>
\<ol\>
<li class=""><strong>Additive changes first</strong> - Add new tables/columns before removing old ones</li>
<li class=""><strong>Dual-write period</strong> - Temporarily write to both old and new schema during transition</li>
<li class=""><strong>Staged rollout</strong> - Update clients to read from new schema while still supporting old schema</li>
<li class=""><strong>Remove old schema</strong> - Once all clients are updated, remove deprecated tables/columns</li>
</ol>
<h2 class="anchor anchorTargetStickyNavbar_Y_NL" id="client-compatibility">Client Compatibility<a href="#client-compatibility" class="hash-link" aria-label="Direct link to Client Compatibility" title="Direct link to Client Compatibility" translate="no">​</a></h2>
<p>During automatic migrations, active client connections are maintained and subscriptions continue to function. However:</p>
\<ul\>
<li class="">Clients may witness brief interruptions in scheduled reducers (such as game loops)</li>
<li class="">Some migrations, such as removing a table, disconnect active clients so they reconnect against the new schema</li>
<li class="">New module versions may remove or change reducers, causing runtime errors for clients calling those reducers</li>
<li class="">Clients won&#x27;t automatically know about schema changes - you may need to regenerate and update client bindings</li>
</ul>

<p>The SpacetimeDB team is working on enhanced migration capabilities, including:</p>
\<ul\>
<li class="">Support for more complex schema transformations</li>
<li class="">Data migration scripts for table modifications</li>
<li class="">Better tooling for previewing migration impacts</li>
<li class="">Automatic client compatibility checking</li>
